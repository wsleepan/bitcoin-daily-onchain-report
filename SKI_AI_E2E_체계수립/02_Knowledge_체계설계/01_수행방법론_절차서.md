# 수행 방법론 절차서 — ② CLX Enterprise Knowledge 관리 체계 설계

각 Phase는 `목적 / Input / Activity / Output / 완료 판단기준 / 참여자 / 사용 템플릿` 으로 정의합니다.
완료 판단기준(Exit Criteria)이 충족되지 않으면 다음 Phase로 넘어가지 않는 것이 원칙이며,
지연 시 범위를 줄이되 판단기준은 낮추지 않습니다.

---

## Phase 0. 착수 · 정렬 (W1)

**목적** — 이후 3.5개월의 판단 기준선을 고정한다. 특히 "Ontology를 어느 수준까지 하는가"에 대한 합의.

**Input** — 제안서/기획서, 이해관계자 목록, 기존 지식 관련 시스템 목록

**Activity**

| # | 활동 | 방법 | 산출 |
|---|---|---|---|
| 0-1 | 용어·수준 합의 | 킥오프 워크숍(2h). README 3장 범위표(In/Out)를 스크린에 띄우고 항목별 확인 | 범위 정의서 (서면 합의) |
| 0-2 | 범위 기준선 확정 | 대상 지식 도메인 / 문서유형 후보 / 시스템 경계 / 제외 항목 명문화 | 범위 기준선 |
| 0-3 | 참조 표준 선정 | README 2장 후보 중 3종 이내로 압축. 선정 사유 기록 | 참조 표준 선정서 |
| 0-4 | 조사 기반 확보 | 인터뷰 대상자 선정(생산자/활용자/시스템운영자 각 3~5명), 일정 확정, 자료 접근 권한 신청 | 인터뷰 계획서 |
| 0-5 | 인터페이스 정의 | ① Legacy 과업 · ③ MLOps 과업과 주고받을 산출물·시점 합의 | 과업 간 인터페이스 표 |

**Output** — 범위 정의서, 참조 표준 선정서, 인터뷰 계획서, 과업 간 인터페이스 표

**완료 판단기준**
- [ ] Ontology 범위(In/Out) 표에 이해관계자 서면 합의 완료
- [ ] 인터뷰 대상자 전원의 일정이 캘린더에 확정
- [ ] 자료 접근 권한 승인 또는 대체 확보 경로 확정

**참여자** — (주) 과업 리드 / (참) CLX 지식 담당, IT 담당 / (승인) PM, CLX Project Leader

**사용 템플릿** — 없음 (워크숍 산출물)

> **주의** — 0-1이 이 과업 전체에서 가장 중요한 30분입니다. 여기서 합의하지 못하면 W7 중간보고에서 반드시 재작업이 발생합니다.

## Phase 1. 지식 현황 진단 (W1 ~ W3)

**목적** — 추정이 아니라 사실로 시작한다. 무엇이 / 어디에 / 어떤 형태로 있고, 실제로 어떻게 쓰이는가.

**Input** — 범위 기준선, 지식문서·시스템 목록, 인터뷰 계획서

**Activity**

| # | 활동 | 방법 | 산출 |
|---|---|---|---|
| 1-1 | 지식자산 인벤토리 | 시스템별 문서유형·건수·포맷·생산주기·소유조직·접근권한 전수 조사 (T01) | 지식자산 인벤토리 |
| 1-2 | 활용 실태 인터뷰 | 생산–검색–활용–갱신 4단계별 반구조화 인터뷰 (T02). 1인 60~90분 | 인터뷰 기록 |
| 1-3 | **실제 질의 수집** | 인터뷰 중 "최근 찾아본 것", "찾다가 포기한 것"을 원문 그대로 수집. 목표 30~50건 | 질의 목록 |
| 1-4 | 활용 시나리오 유형화 | 수집 질의를 유형(사실조회 / 이력추적 / 원인분석 / 절차안내 / 판단지원)으로 군집화 | 활용 시나리오 정의서 |
| 1-5 | 구조화 성숙도 진단 | 문서유형별 4축(양식 표준화 / 메타 부여 / 기계 판독성 / 갱신 관리) 각 1~5점 스코어링 | 성숙도 맵 |
| 1-6 | 대표 유형 선정 | `활용빈도 × AI 활용가치 × 구조화 용이성` 스코어 상위 3~5종 선정 | 대표 문서유형 선정서 |

**Output** — 지식자산 인벤토리, 활용 실태 진단서, 활용 시나리오·질의 유형표, 구조화 성숙도 맵, 대표 문서유형 선정서

**완료 판단기준**
- [ ] 실제 질의 30건 이상 원문 수집 (이 목록이 이후 모든 Phase의 근거)
- [ ] 대표 문서유형 3~5종 선정 및 현업 합의
- [ ] 인벤토리에 문서유형별 건수·보관위치가 공란 없이 채워짐

**참여자** — (주) 과업 리드 / (참) 현업 지식 생산자·활용자, 시스템 운영자 / (검토) CLX 지식 담당

**사용 템플릿** — T01(인벤토리), T02(인터뷰 가이드)

> **자료가 부족한 경우** — 인벤토리를 못 채우면 대표 문서유형 실물 20~30건을 직접 열어 역분석합니다. 문서 자체가 최고의 1차 자료이며, 실제 작성 관행은 규정보다 문서에 남습니다.

## Phase 2. Knowledge 표준 모델 설계 (W2 ~ W5)

> 기대산출물: **CLX Ontology 표준 모델**, **CLX Ontology 설계 및 확장 가이드**

**목적** — CLX 지식을 일관되게 기술하고 서로 연결하기 위한 표준을 정의한다.

**Input** — 활용 시나리오 정의서, 질의 목록, 대표 문서유형 선정서, 참조 표준 선정서

**Activity**

| # | 활동 | 방법 | 산출 |
|---|---|---|---|
| 2-1 | 참조 표준 Gap 분석 | 표준 요소별 `Adopt / Adapt / Author` 판정 및 사유 기록 | 표준 채택 판정표 |
| 2-2 | 지식 분류체계 설계 | 다면 분류(Faceted) — 업무기능 / 설비·공정 / 문서유형 / 생애주기 / 보안등급 (T03) | 분류체계 정의서 |
| 2-3 | 메타데이터 표준 정의 | 공통 필수 메타 12~15개 + 문서유형별 확장 메타. 요소별 정의·필수여부·값 도메인·**자동추출 가능여부** (T04) | 메타데이터 표준 정의서 |
| 2-4 | 통제어휘 사전 구축 | 설비·공정·제품·이상현상 명칭의 대표어/동의어/약어 정규화 (T05) | 통제어휘 사전 |
| 2-5 | 경량 관계 모델 설계 | Phase 1의 질의 유형에서 필요한 관계만 역산. Entity 10~15 / Relation 10 내외 (T06) | Entity–Relation 정의서 |
| 2-6 | **시범 태깅 검증** | 대표 문서유형별 실제 문서 20건에 표준 적용. 2인이 독립 태깅 후 불일치율 측정 | 검증 결과서 |
| 2-7 | 설계·확장 가이드 작성 | 신규 도메인 편입 절차, 명명규칙, 버전·변경관리, 거버넌스 R&R | Ontology 설계 및 확장 가이드 |

**Output** — CLX Ontology 표준 모델(= T03+T04+T05+T06 통합), CLX Ontology 설계 및 확장 가이드

**완료 판단기준** — *정성 합의가 아니라 수치로 판정합니다*
- [ ] 필수 메타 중 **자동추출·양식내재 가능 비율 ≥ 60%**
- [ ] 시범 태깅 2인 독립 수행 시 **판정 불일치율 ≤ 10%**
- [ ] Phase 1 질의 목록의 **80% 이상**이 설계된 분류·메타·관계로 표현 가능
- [ ] 확장 가이드만 보고 제3자가 신규 문서유형 1종을 정의할 수 있음 (예행 검증)

**참여자** — (주) 과업 리드 / (참) 현업 SME(설비·공정 용어), IT 아키텍트 / (검토) CLX 지식 담당

**사용 템플릿** — T03, T04, T05, T06

> **설계 순서 주의** — 분류체계(2-2)를 먼저 완성하고 메타(2-3)로 가지 마십시오. 실제로는 **2-2와 2-3을 함께 2회 반복**하는 것이 빠릅니다. 1차로 거칠게 잡고 2-6 시범 태깅으로 깨진 곳을 찾아 2차 정련합니다.

## Phase 3. 지식 데이터 구조화 및 축적 방안 (W5 ~ W9)

> 기대산출물: **대상별 지식 구조화 방안(OPeX, Tech Report, 근무일지 등)**, **신규 지식 데이터 축적 및 갱신 가이드**

**목적** — 표준을 실제 문서에 적용하는 방법과, 앞으로 쌓아가는 방법을 정의한다.

**Input** — Ontology 표준 모델, 대표 문서유형 선정서, 성숙도 맵

**Activity**

| # | 활동 | 방법 | 산출 |
|---|---|---|---|
| 3-1 | 문서유형별 구조 표준 | 유형별 섹션 구조 / 필수 항목 / 청킹 단위 / 표·이미지 처리 / 비정형→반정형 전환 규칙 (T07) | 대상별 지식 구조화 방안 |
| 3-2 | 기존 지식 전환 방안 | 전환 대상 선별 기준(최신성·활용도·품질), 전환 방식(자동추출 / 반자동 / 수동) 및 물량·기간 산정 | 전환 계획 |
| 3-3 | 신규 축적·갱신 가이드 | 생산 시점 메타 부여 방식(**양식 내재화가 원칙**), 승인·검증 흐름, 갱신 주기, 폐기 기준, R&R (T08) | 축적 및 갱신 가이드 |
| 3-4 | 품질 기준 정의 | 완전성 / 정확성 / 최신성 / 일관성 4지표의 정의·측정식·목표치 | 지식 품질 기준 |
| 3-5 | 파일럿 전환 검증 | 대표 유형별 실제 문서 50건 전환 → 품질 지표 측정 → 구조 표준 보정 | 파일럿 결과서 |

**Output** — 대상별 지식 구조화 방안, 신규 지식 데이터 축적 및 갱신 가이드

**완료 판단기준**
- [ ] 대표 유형 3종 전부에 대해 구조 표준 확정 및 파일럿 50건 전환 완료
- [ ] 파일럿 결과 품질 4지표 측정치 확보 및 목표치 대비 판정
- [ ] 갱신 가이드에 **역할별 R&R과 주기가 명시**되어 있고 해당 조직이 수용 확인

**참여자** — (주) 과업 리드 / (참) 문서유형별 현업 담당, 데이터 담당 / (검토) CLX 지식 담당

**사용 템플릿** — T07, T08

> **청킹 단위가 핵심** — AI Agent 활용을 전제하므로, 구조화의 실질은 "검색·인용 단위를 무엇으로 자를 것인가"입니다. 근무일지는 일자·설비 단위, Tech Report는 절(Section) 단위, OPeX는 과제·조치 단위처럼 유형별로 다르며, 이 결정이 Knowledge Hub 요건까지 이어집니다.

## Phase 3B. 도메인 특화 LLM 데이터 확보 방향성 (W5 ~ W12, Phase 3과 병렬)

> 기대산출물: **필요 데이터 유형 및 요건**, **학습 데이터 축적 우선순위 및 개발 로드맵**

**목적** — 도메인 LLM/Agent가 필요로 하는 데이터를 식별하고, 무엇부터 확보할지 정한다.

**Input** — 활용 시나리오 정의서, 질의 목록, 지식자산 인벤토리

**Activity**

| # | 활동 | 시기 | 방법 | 산출 |
|---|---|---|---|---|
| 3B-1 | 외부 사례 조사 | W5~W6 | 제조·화학 도메인 LLM 구축 사례의 데이터 유형·규모·확보방식·투입 조사 | 외부 사례 조사서 |
| 3B-2 | 시나리오별 데이터 식별 | W7~W8 | 시나리오 → 필요 지식 → 데이터 유형(문서/이력/대화/도면/코드) → 요건(형식·규모·라벨·민감도) (T09) | 필요 데이터 유형 및 요건 |
| 3B-3 | 확보 방식 설계 | W9~W10 | 방식별(기존 활용 / 신규 생성 / 합성 / 외부 도입) 비용·기간·리스크·보안 제약 비교 | 데이터 확보 방식 |
| 3B-4 | 우선순위·로드맵 | W11~W12 | `가치(활용도×효과) × 실현가능성(확보난이도×비용)` 2×2 매핑 → 단계별 로드맵 (T10) | 축적 우선순위 및 개발 로드맵 |

**Output** — 필요 데이터 유형 및 요건, 학습 데이터 축적 우선순위 및 개발 로드맵

**완료 판단기준**
- [ ] 모든 데이터 요건이 Phase 1의 **실제 질의/시나리오로 역추적 가능** (근거 없는 요건 0건)
- [ ] 우선 축적 대상 Top N에 대해 확보 방식·소요 기간·필요 투입이 산정됨
- [ ] 보안·반출 제약이 각 확보 방식별로 판정됨

**참여자** — (주) 과업 리드 / (참) AI/데이터 담당, 보안 담당 / (검토) ③ MLOps 과업 담당

**사용 템플릿** — T09, T10

> **③ MLOps 과업과의 접점** — 학습 데이터 파이프라인·버전관리는 ③의 MLOps 영역입니다. 본 과업은 "무슨 데이터가 왜 필요한가"까지 정의하고, "어떻게 운영·관리하는가"는 ③으로 넘깁니다. W12에 인계 회의를 배치하십시오.

## Phase 4. Enterprise Knowledge Hub 구축 방안 수립 (W9 ~ W13)

> 기대산출물: **Enterprise Knowledge Hub 사용자 요건**, **Enterprise Knowledge Hub 구축 방안**

**목적** — 표준과 구조화 방안을 담아 운영할 그릇의 요건과 구축 방향을 정한다.

**Input** — Ontology 표준 모델, 구조화 방안, 축적·갱신 가이드, 활용 시나리오

**Activity**

| # | 활동 | 시기 | 방법 | 산출 |
|---|---|---|---|---|
| 4-1 | 외부 사례 및 전사 체계 검토 | W9~W10 | 외부 Knowledge Hub 사례 + **기존 CLX/전사 플랫폼 현황** 검토 (중복 투자 방지) | 사례·현황 검토서 |
| 4-2 | 사용자 요건 정의 | W10~W11 | 페르소나별 User Story(`~로서 ~하기 위해 ~하고 싶다`) + 수용기준 (T11) | Knowledge Hub 사용자 요건 |
| 4-3 | 기능·비기능 요건 정의 | W11 | 검색·탐색 / 메타 관리 / 권한 / 수집·연계 / 품질 모니터링 / **Agent 연계 API** / 성능·확장성 | 요건 정의서 |
