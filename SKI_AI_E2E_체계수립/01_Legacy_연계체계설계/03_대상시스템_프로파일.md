> 본 문서는 방법론의 **적용 대상 특성**을 정의합니다. Phase 1~7의 활동이 시스템별로 어떻게 달라지는지의 근거입니다.

## 1. 시스템별 프로파일

### OASIS — 생산관리 플랫폼

| 항목 | 내용 |
|---|---|
| 데이터 성격 | **트랜잭션 · 업무 상태** (생산계획, 작업지시, 실적, 품질, 재고) |
| 데이터 단위 | 오더 / 배치 / 로트 / 교대 |
| 시간 축 | 생산일자 · 교대 (물리적 시각과 다름) |
| 갱신 빈도 | 이벤트 발생 시 (수 분~시간) |
| 규모 | 중 |
| 주 Agent 수요 | 실적·계획 조회, 이상 시 생산 영향 판단, 품질 이력 추적 |
| 지배 Action Pattern | P-READ, P-ANALYZE, **(P-ACT 수요 큼)** |

**설계 시사점**

- **쓰기(P-ACT) 압력이 가장 큰 시스템입니다.** "Agent가 작업지시를 내면 좋겠다", "실적을 대신 입력했으면" 같은 요구가 반드시 나옵니다. → 원칙 2(읽기/쓰기 분리)가 가장 첨예하게 걸리는 지점이며, W1 범위 기준선에서 **OASIS 쓰기를 1차 범위 밖으로 명시적으로 빼는 것**이 중요합니다.
- 업무 상태 코드가 다수 존재합니다 (오더 상태, 품질 판정, 승인 단계 등). → **A3(의미 명확성) 최대 이슈**. 코드값 사전 없이는 Agent가 상태를 오해합니다.
- 권한이 **조직 · 공장 · 공정 · 역할**에 강하게 묶여 있습니다. → Phase 5에서 **사용자 권한 위임(On-Behalf-Of)이 사실상 필수**. Service Account 단일 권한으로는 보안 승인이 나기 어렵습니다.
- **생산일 정의가 물리적 날짜와 다릅니다** (예: 06:00~익일 06:00). RTDB 타임스탬프와 조인할 때 반드시 어긋납니다. → 3장 시간 축 표준 참조.

### OCEAN H — 설비관리 통합 플랫폼

| 항목 | 내용 |
|---|---|
| 데이터 성격 | **마스터 + 이력** (설비 마스터, 정비이력, 예방정비, 고장·작업오더, 스페어) |
| 데이터 단위 | 설비 / 작업오더 / 정비 건 |
| 시간 축 | 작업일자 · 발생일시 |
| 갱신 빈도 | 이벤트 발생 시 |
| 규모 | 중 (이력 누적으로 증가) |
| 주 Agent 수요 | 설비 이상 원인 조회, 유사 정비사례 탐색, 설비 스펙·이력 확인 |
| 지배 Action Pattern | P-READ, **P-SEARCH**, P-ANALYZE |

**설계 시사점**

- **설비 마스터가 전사 공통 식별자의 원천입니다.** 이 과업에서 가장 전략적인 자산이며, 다른 두 시스템과의 조인 키가 여기서 나옵니다. → Phase 3의 식별자 표준화는 **OCEAN H 설비 마스터를 기준으로** 설계합니다.
- **계층 구조**(플랜트–유닛–설비–부품)를 가집니다. Agent 질의는 대개 중간 계층("3호기 압축기")으로 들어오는데, 데이터는 말단 계층에 있습니다. → 계층 탐색·상하위 롤업 조회 요건이 별도로 필요합니다.
- 정비이력의 **조치 내용·고장 현상이 자유서술 텍스트**입니다. → **② Knowledge 과업과 경계가 가장 애매한 지점.** 경계 규칙을 아래 4장에 명시했습니다.
- 마스터 품질(중복 설비, 폐기 미반영, 명칭 불일치)이 진단의 핵심입니다. → **A2(데이터 구조) 취약 예상.**

### RTDB — 공정 실시간 데이터 (가정: 태그 시계열 히스토리안)

| 항목 | 내용 |
|---|---|
| 데이터 성격 | **대용량 시계열** (태그별 측정값) |
| 데이터 단위 | 태그 × 타임스탬프 |
| 시간 축 | 밀리초~초 단위 절대 시각 |
| 갱신 빈도 | 초 단위 연속 |
| 규모 | **대** (타 시스템 대비 자릿수 차이) |
| 주 Agent 수요 | 이상 시점 공정값 추이, 정상 대비 편차, 실시간 상태 감시 |
| 지배 Action Pattern | P-ANALYZE, **P-MONITOR** (P-ACT 없음) |

**설계 시사점**

- **범용 REST 조회로 감당되지 않습니다.** "지난달 3호기 온도 추이"는 수백만 포인트입니다. → **집계·다운샘플링 전용 API** 또는 **배치 복제(분석용 저장소)** 가 필요하며, 이 판단이 Phase 4의 시스템별 차등 설계 근거입니다.
- **태그명이 의미 불명입니다** (`FIC-1203.PV` 등). Agent는 "3호기 압축기 토출 온도"로 묻지 태그명으로 묻지 않습니다. → **A3(의미 명확성) 최악의 시스템**이며, **태그 ↔ 설비 ↔ 물리량 매핑이 이 과업의 핵심 과제 중 하나**입니다. 이 매핑 없이는 RTDB 연계가 성립하지 않습니다.
- 쓰기 수요가 없어 권한 설계는 상대적으로 단순합니다. 다만 공정값 자체가 **영업비밀 민감도**를 가질 수 있어 열람 범위 통제가 필요합니다.
- 실시간 감시(P-MONITOR)는 요청–응답이 아니라 **이벤트/구독** 모델이 적합합니다. → 연계 방식이 다른 두 시스템과 근본적으로 갈립니다.
- **③ MLOps 과업과의 접점** — 이상감지 모델의 학습·추론 데이터가 여기서 나옵니다. 데이터 접근 경로를 ①에서 정의하고 파이프라인 운영은 ③으로 넘깁니다.

## 2. 시스템 비교 요약

| 축 | OASIS | OCEAN H | RTDB |
|---|---|---|---|
| 데이터 성격 | 트랜잭션·상태 | 마스터·이력 | 시계열 |
| 규모 | 중 | 중 | **대** |
| 실시간성 요구 | 중 | 저 | **고** |
| 쓰기 수요 | **고** | 중 (작업오더) | 없음 |
| 권한 복잡도 | **고** | 중 | 저 |
| 예상 취약축 | A3 상태코드 의미<br>A4 권한 세분성 | A2 마스터 품질<br>A3 이력 텍스트 | **A3 태그 의미**<br>A1 전용 프로토콜 |
| ② Knowledge 접점 | 낮음 | **높음** (정비이력 텍스트) | 없음 |
| ③ MLOps 접점 | 중 | 낮음 | **높음** (학습 데이터) |

> **이 표가 원칙 3("연계 방식을 하나로 통일할 필요 없다")의 구체적 근거입니다.** 성격이 이렇게 다른 세 시스템을 동일 방식으로 붙이려는 시도가 가장 흔한 실패 경로입니다.

## 3. 연계 방식 가설 (Phase 4에서 검증할 출발점, 결론 아님)

| 시스템 | 유력 연계 방식 | 근거 | 검증 포인트 |
|---|---|---|---|
| OASIS | REST/OpenAPI + 전사 Gateway | 권한 세분성·감사 필요, 향후 쓰기 확장 대비 | 기존 API 성숙도, 권한 위임 지원 여부 |
| OCEAN H | REST + **검색 색인 계층** (MCP 유력) | 계층 탐색·이력 텍스트 검색, 도구 다양성 | 색인 대상 범위, ②와의 중복 |
| RTDB | **전용 집계 API + 배치 복제** (+ P-MONITOR는 이벤트 구독) | 대용량 시계열, 범용 REST 부적합 | 집계 API 존재 여부, 복제 저장소 필요성 |

**MCP 적용 가설** — 도구 수가 많고 Agent가 자율적으로 골라야 하는 **OCEAN H 탐색·검색 계열**에서 실익이 가장 큽니다. 반대로 RTDB 대량 집계는 MCP로 감싸도 이득이 없고, OASIS 트랜잭션은 Gateway 정책 준수가 우선입니다.
→ **전면 MCP도, 전면 배제도 아닌 "부분 적용"이 유력한 결론**이며, Phase 4-4에서 근거와 함께 확정합니다.

## 4. 진짜 난제 — 시스템 간 조인

Agent 질의는 **대부분 시스템 경계를 넘습니다.**

> *"3호기 압축기 지난달 트립, 원인이 뭐였고 생산에 얼마나 영향 있었나?"*
> → **OCEAN H** (설비 식별 + 고장·정비 이력) + **RTDB** (트립 전후 공정값 추이) + **OASIS** (해당 시간대 생산 실적)

시스템별로 잘 붙여도 이 질문에 답할 수 없습니다. **세 시스템이 공통 축으로 연결되어야** 합니다.

### 4-1. 공통 식별자 축 (Join Key)

| 축 | 원천 | 문제 | 필요 조치 |
|---|---|---|---|
| **설비** | OCEAN H 설비 마스터 | RTDB 태그와 매핑 없음, OASIS 오더는 공정 단위 | 설비 ↔ 태그 매핑, 설비 ↔ 공정 매핑 구축 |
| **시간** | 각 시스템 상이 | RTDB=절대 시각(ms), OASIS=생산일·교대, OCEAN H=작업일자 | 기준 시간축 정의, 생산일·교대 경계 변환 규칙 |
| **공정·유닛** | (확인 필요) | 시스템별 코드 체계 상이 가능 | 표준 공정 코드 및 매핑표 |
| **배치·오더** | OASIS | 설비·시계열과 연결 고리 부재 | 오더 ↔ 설비 ↔ 시간구간 매핑 |

> **이 매핑 구축이 ① 과업의 숨은 핵심 산출물입니다.** 개별 시스템 API를 아무리 잘 만들어도 조인 키가 없으면 Agent는 시스템 하나짜리 질문에만 답할 수 있고, 현업이 실제로 궁금해하는 것은 대부분 횡단 질문입니다.

### 4-2. 조인 책임을 어디에 둘 것인가 (Phase 4 결정 사항)

| 안 | 방식 | 장점 | 단점 |
|---|---|---|---|
| A. Agent가 조합 | Agent가 여러 도구를 호출해 결과를 스스로 결합 | 유연, 구축 부담 적음 | **부정확** (LLM이 조인 규칙을 임의 적용), 대량 데이터 불가 |
| B. 통합 조회 계층 | 사전 정의된 통합 뷰·마트를 제공 | 정확, 성능 | 구축 비용, 질의 유형 고정 |
| C. **하이브리드** | 식별자·매핑은 표준 계층이 보장하고, 조합은 Agent가 수행 | 현실적 균형 | 매핑 계층 구축·유지 필요 |

→ 방법론은 **C를 기본 가설**로 두되, 고빈도 횡단 질의 유형은 B(통합 뷰)로 승격하는 판정 기준을 Phase 4에서 정의합니다.

## 5. 타 과업과의 경계 (시스템 구체화)

| 대상 | ① Legacy (본 과업) | ② Knowledge | ③ MLOps·AgentOps |
|---|---|---|---|
| OASIS 정형 데이터 | ● 전담 | — | — |
| OCEAN H 마스터·정형 이력 | ● 전담 | — | — |
| **OCEAN H 정비이력 자유서술 텍스트** | 필드 접근·메타 정의 | **구조화·검색 대상** | — |
| RTDB 시계열 | ● 접근 경로 정의 | — | 학습·추론 파이프라인 |
| 비정형 문서 (Tech Report, OPeX 등) | — | ● 전담 | — |
| Agent 실행·운영·모니터링 | — | — | ● 전담 |

**경계 규칙**
1. **시스템의 정형 필드 = ①**, **자유서술 텍스트 지식 = ②**
2. OCEAN H 정비이력처럼 한 레코드에 둘이 섞인 경우 → **①이 접근 경로·필드 메타를 정의하고, ②가 텍스트 구조화·검색 요건을 정의**. Phase 3-2 메타 요건 작성 시 ②와 합동 리뷰
3. RTDB 데이터의 **접근 경로는 ①**, 그 데이터로 만드는 **모델·파이프라인은 ③**
