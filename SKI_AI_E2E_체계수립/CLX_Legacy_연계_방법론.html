01

여섯 개의 질문

“AI와 Legacy를 어떻게 연결할 것인가”는 하나의 질문이 아닙니다. 섞어서 다루면 결론이 나오지 않습니다. 방법론은 이 여섯을 분리해 순서대로 답합니다.

#질문성격담당
Q1Agent는 Legacy에 무엇을 요구하는가수요 정의Phase 1
Q2Legacy는 지금 얼마나 준비되어 있는가현황 진단Phase 2
Q3어떤 방식으로 연결할 것인가 (MCP / API / Gateway)연계 설계Phase 4
Q4누구의 권한으로 접근하는가권한 설계Phase 5
Q5바뀌었을 때 무엇이 영향받는지 아는가변경 관리Phase 6
Q6시스템을 가로지르는 질문에 어떻게 답하는가식별자 · 조인Phase 3·4

Q3만 논의하면 반드시 막힙니다. Q1이 없으면 선정 기준이 없고, Q2가 없으면 무엇을 고쳐야 하는지 모르며, Q4가 없으면 보안 승인을 못 받습니다.

Q6은 가장 늦게 발견되고 가장 비싼 문제입니다. 시스템별로 잘 붙여놓고도 “3호기 압축기 트립이 생산에 얼마나 영향 줬나” 같은 횡단 질문에 답하지 못합니다. 현업이 실제로 궁금해하는 것은 대부분 횡단 질문입니다.

02

7대 설계 원칙

체계가 사실상 백지에서 시작하므로 “무엇을 먼저 정하느냐”가 성패를 가릅니다. 아래 일곱이 이후 모든 Phase 순서의 근거입니다.

01

Action Pattern이 연계 요건을 결정한다

연계 방식을 먼저 고르고 Agent를 맞추면 반드시 재작업이 발생합니다. Agent 유형 → Action Pattern → 인터페이스 요건 → 연계 방식 순으로 역산합니다.

02

읽기와 쓰기는 완전히 다른 문제다

조회는 데이터 구조·검색성 문제이고, 쓰기는 권한·감사·롤백 문제입니다. 난이도가 자릿수 단위로 다릅니다. 1차 범위를 읽기 전용으로 고정하지 않으면 보안·현업 검토에서 전체가 멈춥니다.

03

MCP는 배관이 아니라 어댑터다

이 과업 최대의 오해 지점입니다. MCP를 도입해도 Legacy가 Agent-ready가 되지 않습니다. MCP는 L4 도구 노출 규약이며, 그 아래 Legacy API와 의미 계층이 없으면 감쌀 대상이 없습니다.

04

전사 방침에 종속하고, CLX는 적용 기준만 만든다

CLX가 독자 연계 경로를 설계하면 전사 거버넌스와 충돌하고 중복 투자 지적을 받습니다. 산출물을 (a) CLX 적용 기준과 (b) 전사 개선 요청 2갈래로 분리합니다.

05

진단은 시스템별이 아니라 공통 축으로

시스템을 각각 진단하면 개별 개선 목록만 나오고 통합 로드맵이 나오지 않습니다. Agent-Readiness 6축(인터페이스 · 데이터 구조 · 의미 명확성 · 권한 세분성 · 관측·감사 · 변경관리)으로 평가하면 공통 과제와 특화 과제가 자동으로 갈립니다.

06

세 시스템은 하나의 방식으로 붙지 않는다

규모가 자릿수 단위로 다르고, 실시간성 요구가 다르고, 쓰기 수요가 다릅니다. “전부 REST로” 또는 “전부 MCP로” 통일하려는 시도가 가장 흔한 실패 경로입니다.

07

통합의 실질은 API가 아니라 공통 식별자다

개별 API를 아무리 잘 만들어도 설비 · 시간 · 공정 · 오더 4개 축의 식별자가 정합되지 않으면 횡단 질문에 답할 수 없습니다. 이것이 ① 과업의 숨은 핵심 산출물입니다.

04

Phase 0–8 수행 절차

기획서의 3단계 흐름(현황 분석 → To-be 방향성 → 실행과제)을 유지하되 실행 가능한 Phase로 분해했습니다. 완료 판단기준은 정성 합의가 아니라 수치로 정의합니다.

Stage 1 · 현황 분석W1–W6
P0착수 · 정렬W1

이후 3.5개월의 판단 기준선을 고정한다. 특히 1차 범위를 읽기 전용으로 긋는 것과 MCP 판단 시점을 뒤로 미루는 것에 대한 합의.

완료 판단기준
  • 1차 범위(읽기 전용) 서면 합의 — 미합의 시 Phase 5 일정이 성립하지 않음
  • MCP 판단 시점 합의 (Phase 4)
  • 시스템별 담당자 지정 및 인터뷰 일정 확정
  • 전사 Endpoint/Gateway 방침 확보 또는 미확정 사실 확인 + 가정 명시
  • OCEAN-H vs TDMS 설비 마스터 중복 확인 착수

이 과업에서 가장 중요한 30분입니다. “MCP 얹으면 되는 것 아니냐”는 기대를 W1에 정리하지 못하면, Phase 2·3의 Legacy 고도화 과제가 “불필요한 일”로 취급됩니다.

P1CLX AI Agent 현황 및 유형 분석W1–W3

Legacy에 대한 수요를 확정한다. 이후 모든 설계의 근거. 기존 AI 과제 MP의 13종 구성 기술과 스마트플랜트 2.0 40개 과제가 이미 모집단이므로, 발굴이 아니라 요구의 역산이다.

완료 판단기준
  • Agent 유형이 5–8종 이내로 수렴 (10종 넘으면 유형화 실패 — 재분류)
  • 모든 유형이 Action Pattern으로 표현되고 정량 요건(응답시간·데이터량) 기재
  • 수요 매트릭스의 ‘미정’ 셀 0건
  • P-ACT(쓰기) 요구가 별도 식별되어 1차 범위 밖으로 분리 OASIS 집중 예상
  • 횡단 질의 비중 측정 + 대표 횡단 질의 5건 선정
P2Legacy Agent-Readiness 진단W3–W6

Legacy의 공급 현황을 6축 공통 기준으로 진단하고 수요와의 Gap을 확정한다. 시스템별 담당 조직이 다르므로 병렬 진행이 필수.

완료 판단기준
  • 대상 시스템 전부에 6축 점수와 판정 근거 기록 (점수만 있으면 무효)
  • 실제 호출 검증 최소 3건 — RTDB 대량 구간 조회 1건 필수 포함
  • Phase 1 수요 요건의 100%가 Gap 판정을 받음
  • 공통 과제와 시스템 특화 과제 분리

RTDB 대량 구간 조회 검증(W4)이 가장 중요한 단일 검증입니다. 태그 1개월 이력 조회에서 타임아웃이 확인되면 Phase 4의 연계 방식 결론이 즉시 달라지며, 이를 W10에 발견하면 아키텍처 재작업입니다.

Stage 2 · To-be 방향성W4–W13
P3데이터 · 메타 구조 고도화W4–W9

Agent가 정확하게 해석할 수 있는 데이터 상태를 정의한다. 핵심 신설 활동은 3-2 시스템 횡단 식별자 표준화.

완료 판단기준
  • 대표 횡단 질의 5건이 공통 식별자만으로 조인 가능함이 확인됨
  • 4개 축 전부에 기준 원천 지정 및 사유 문서화
  • Before/After 예시 3건 — OASIS 상태코드 · OCEAN-H 설비 계층 · RTDB 태그 각 1건
  • 설계 가이드가 체크리스트 형태로 즉시 적용 가능
P4연계 구조 및 적용 기준 수립 ★W6–W11

연결 방식을 선정하고 기준을 세운다. 이 과업 Key Question에 대한 직접적 답. 상세는 06장 참조.

완료 판단기준
  • 5개 Action Pattern 전부에 연계 방식 지정 + 사유 문서화
  • MCP 채택 판단 완료 — 조건부면 조건 명시
  • 산출물이 (a) CLX 적용 기준 / (b) 전사 협의사항 2갈래로 분리
  • 대표 횡단 질의 5건의 End-to-End 호출 흐름도
  • Phase 5 권한 모델과 상충 없음 (교차 확인 회의 실시)
P5권한 관리체계 고도화W7–W12

“누구의 권한으로 접근하는가”에 답한다. 보안 승인의 관문.

완료 판단기준
  • 모든 Action Pattern에 권한 모델 지정
  • 결과 필터링 요건 명시 — Agent가 요청자 권한 밖 데이터를 반환하지 않음
  • Agent 연쇄 호출 시 권한 전파 규칙 정의
  • 보안 담당 사전 검토 의견 수령 및 반영

실무의 핵심 난제. Agent 고유 권한(Service Account)은 구현이 쉽지만 최소권한 위배로 승인이 어렵고, 사용자 권한 위임(OBO)은 안전하지만 토큰 전파가 복잡합니다. 대부분 혼합으로 수렴하며, 어느 패턴에 무엇을 적용할지 문서로 못박는 것이 산출물의 실질입니다.

P6Lineage · 변경관리 체계 설계W9–W13

“무언가 바뀌었을 때 무엇이 영향받는지 안다”를 성립시킨다.

완료 판단기준
  • 관리 대상 구성요소 빠짐없이 식별 — 프롬프트 · 도구 정의 누락이 가장 흔함
  • 대표 변경 시나리오 3건의 영향 경로 End-to-End 작성
  • ③ MLOps/AgentOps 과업과 역할 경계 합의

Legacy 스키마 변경이 Agent 응답을 조용히 망가뜨리는 것이 이 Phase가 막으려는 사고입니다. 전통적 연계는 오류가 나지만, Agent는 그럴듯한 틀린 답을 반환합니다.

Stage 3 · 실행과제W10–W14
P7Agent-ready Legacy 목표구조 및 고도화 방안W10–W13

Phase 3–6 요건을 시스템별로 종합한 To-be 구조도와 단계적 전환 로드맵. 각 고도화 항목은 Phase 2 Gap 또는 Phase 1 요구사항으로 역추적 가능해야 한다.

P8실행과제 정의 및 통합W12–W14

모든 과제를 전사 공통·협의 / CLX 특화 로 분류하고, 차년도 추진 범위·수행계획을 의사결정 가능한 수준으로 제시한다. 기대산출물 12종 제출.

데이터 구조 · 메타데이터 관리

API는 Agent를 연결하지만, 메타데이터는 Agent를 정확하게 만듭니다.

전통적 연계에서 메타데이터는 “있으면 좋은 것”이었습니다. 호출하는 쪽이 사람이 만든 프로그램이었고, 개발자가 사양서를 읽고 의미를 코드에 박아 넣었기 때문입니다. Agent는 런타임에 데이터의 의미를 스스로 해석하고, 근거가 없으면 그럴듯하게 지어냅니다. 그래서 메타데이터는 정확성 요건으로 승격됩니다. 이것이 이 과업이 “API 개발 프로젝트”가 아닌 이유입니다.

기획서의 “AI Agent 연계 구조”는 통상 Agent–Legacy 연계로만 해석됩니다. 그러나 그룹 방향이 ‘1인 1에이전트’이고 울산CLX에 스마트플랜트 2.0 과제 40여 개가 이미 돌아갑니다. Agent 수가 늘면 문제의 성격이 바뀝니다.

권한 전파 원칙 — 최대 난제

중간 Agent가 자기 권한으로 조회하면 사용자가 볼 수 없는 데이터가 답변에 섞여 나옵니다. 사용자는 그것이 권한 밖 데이터인지 알 수 없습니다.

#원칙내용
A1최소 권한 승계하위 Agent 유효 권한 = min(사용자 권한, Agent 권한). 절대 확대되지 않음
A2사용자 컨텍스트 필수 전파모든 Agent 간 호출에 요청자 신원 · 권한 컨텍스트 동반. 익명 호출 금지
A3전파 깊이 제한위임 체인 최대 깊이 3. 초과 시 차단
A4권한 밖 명시권한으로 제외된 데이터가 있으면 “일부 결과가 권한으로 제외됨”을 응답에 표시
A5감사 이중 기록최종 사용자 + 호출 Agent 체인 전체를 로그에 기록
A6쓰기 위임 금지Agent가 다른 Agent에 쓰기 작업을 위임할 수 없음

A4가 실무에서 가장 자주 빠집니다. 권한으로 필터링된 결과를 그대로 반환하면 사용자는 “데이터가 없다”고 이해합니다. 안전사고 원인 분석에서 이는 치명적입니다.
