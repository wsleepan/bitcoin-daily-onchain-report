## 1. 사업장 규모 — 왜 이 과업이 어려운가

| 항목 | 규모 | 출처 |
|---|---|---|
| 부지 | 약 **250만 평** | `[확인]` |
| 공정 설비 | 약 **60만 기** | `[확인]` |
| OCEAN-H 전환 데이터 | **1,000만 건 이상** | `[확인]` |
| 통합된 기존 시스템 | **15종 이상** | `[확인]` |
| 데이터 정제 완료율 | **80% 이상** (구축 시점) | `[확인]` |

**컨설팅 시사점**

- 설비 60만 기 규모에서 **"어느 설비인지 특정하는 것" 자체가 난제**입니다. Agent가 "3호기 압축기"라고 받았을 때 후보가 수십 개일 수 있습니다. → 원칙 7(식별자)의 중요성이 일반 제조업보다 훨씬 큽니다.
- **데이터 정제 80%는 양날의 검**입니다. 상위 80%는 이미 정비돼 있어 Phase 2 진단 부담이 줄지만, **남은 20%가 어디인지**가 Agent 신뢰성을 좌우합니다. Phase 2에서 "정제된 80%"와 "미정제 20%"의 경계를 반드시 식별하십시오. Agent는 미정제 구간에서 조용히 틀린 답을 냅니다.
- 15종 시스템 통합 경험이 이미 있다 → **조직에 통합 프로젝트 학습이 축적돼 있습니다.** OCEAN-H 구축 시의 마스터 정비 방법론·거버넌스를 그대로 참조·재사용할 수 있습니다. Phase 0에서 당시 산출물 확보를 요청하십시오.

## 2. 대상 시스템 연혁 및 성격

### OCEAN-H `[확인]`
- 정식 명칭: **Optimized & Connected Enterprise Asset Network – Hub**
- 차세대 **설비관리(EAM)** 통합 플랫폼
- 2015년 필요성 인식 → **2019년 자체 설계·개발 착수 → 약 2년 만에 완성 → 2021년 6월 가동**
- 기존 **15종 이상 시스템을 단일 플랫폼으로 통합**
- 현장 실제 업무 프로세스를 반영해 설계 (사용자 편의성 중시)
- **OCEAN-P**: 협력회사 포탈. 설비·보수 업무 데이터를 협력사와 **공동 관리**
- **PTC와 협력** — AR(증강현실) 접목 스마트플랜트 솔루션, 사업화 추진 중
- DCR(Digital Contest & Review) Best of Best 수상

**컨설팅 시사점**
- **자체 설계·개발 시스템**입니다. 상용 패키지(SAP PM 등)가 아니므로 **표준 API가 없을 가능성이 높고**, 반대로 **내부 개발 조직이 있어 API 추가가 상대적으로 용이**합니다. → Phase 2에서 A1(인터페이스) 진단 시 "API 유무"보다 **"API를 추가할 수 있는 조직·절차가 있는가"** 를 확인하는 것이 실질적입니다.
- **OCEAN-P(협력사 포탈)의 존재는 권한 설계에 직접적 영향**을 줍니다. 정비 데이터에 협력사 인원 정보가 섞여 있고, 협력사도 데이터 생산 주체입니다. → Phase 5에서 **사내 인원 / 협력사 인원 / Agent** 3주체의 권한 모델을 다뤄야 합니다. 이는 일반적인 사내 시스템 권한 설계보다 한 단계 복잡합니다.
- PTC 협력(AR) → OCEAN-H가 **PTC 스택(ThingWorx 등)과 연동**돼 있을 가능성 `[추정]`. 사실이면 ThingWorx REST API가 이미 존재할 수 있어 A1 점수가 예상보다 높을 수 있습니다. **Phase 0에서 확인하십시오.**

### OASIS `[확인]`
- **생산관리** 기간 시스템
- 2016년 국내 석유화학 업계 **최초 스마트플랜트 도입** 시기에 구축
- OCEAN-H와 함께 "데이터 및 업무 관리 기간 시스템"으로 DT 추진 기반

**컨설팅 시사점**
- OCEAN-H(2021)보다 **5년 앞선 시스템**입니다. 아키텍처 세대가 다를 가능성이 높습니다 `[추정]`. → Phase 2 진단에서 **OASIS의 A1(인터페이스) 점수가 OCEAN-H보다 낮게 나올 것으로 예상**하고 시간을 더 배분하십시오.

### RTDB `[추정]`
- 공개 자료에서 직접 확인되지 않음
- 공정 자동 운전·자동 제어·고장 예측 과제가 다수 추진 중인 점으로 보아 **공정 실시간 데이터 저장소(히스토리안)가 존재**하는 것은 확실
- **착수 시 정확한 제품·구조 확인 필요** (PI System / 자체 구축 / DCS 연동 방식)

## 3. AI/DT 추진 현황 — 이 과업의 배경

### 스마트플랜트 1.0 (2016~) `[확인]`
- 국내 석유·화학 업계 최초 도입
- OASIS(생산관리), OCEAN-H(설비관리) 등 **기간 시스템 구축 = 데이터 기반 확보 단계**

### 스마트플랜트 2.0 (2024~) `[확인]`
- **AI/DT를 적용한 약 40개 과제**를 울산CLX에 적용 중
- 적용 3개 분야: **공정운전 / 설비관리 / SHE(안전·보건·환경)**
- 주요 과제:
  - 공정 자동 운전 프로그램
  - 공정 자동 제어 고도화
  - **설비 고장예측 솔루션**
  - **울산CLX 통합 안전 모니터링 체계**
- 로봇개·드론 등 현장 로보틱스 도입
- 기대효과: **연간 100억 원 이상 비용 개선**
- 자체 구축 솔루션의 **지식자산화 → 신규 사업모델 확장** 계획

### 그룹 차원 AI 동향 `[확인]`
| 항목 | 내용 | 본 과업 시사점 |
|---|---|---|
| SK이노베이션 — **MS Azure 기반 생성형 AI 플랫폼** | 엔지니어링 자료 검색·분석, 데이터 처리, 보고서 작성 자동화 | **이미 RAG형 Agent가 가동 중.** Phase 1의 "현황 조사"가 백지가 아님 |
| SK이노베이션 × SKT — **명장 AI 플랫폼** 공동 개발 | 자체 AI 플랫폼 | 플랫폼 계층이 이미 정해져 있을 수 있음 → Phase 4 아키텍처 제약 조건 |
| **SKT — AI 에이전트에 사번 부여** (AX 혁신 2.0, 2026) | Agent에 **소속·직무·권한 할당**, 입사~퇴사 유사 절차로 관리. **데이터·보안 접근 권한 규정** 마련 | **Phase 5 권한 모델의 그룹 내 선례.** 아래 5장 참조 |
| 최태원 회장 — **'1인 1에이전트'** | 그룹 차원 AI 대전환 방향 | Agent 수가 폭증할 것을 전제로 설계해야 함 → Agent 간 연계(A2A) 필요성의 근거 |
| SK AX — **에이전틱 엔터프라이즈** | 기획서 9페이지 수행조직에 SKAX 명시 | 수행사 자체 방법론·자산과 정합 확인 필요 |

**컨설팅 시사점 — 가장 중요한 3가지**

1. **"Agent가 아직 없다"는 전제로 접근하면 안 됩니다.** Azure 기반 생성형 AI가 이미 엔지니어링 자료 검색에 쓰이고 있고, 스마트플랜트 2.0 과제 40개 중 상당수가 AI입니다. → **Phase 1은 "무엇을 만들까"가 아니라 "이미 돌아가는 것들이 Legacy를 어떻게 쓰고 있나"의 조사**입니다.

2. **'1인 1에이전트' 방향은 Agent 수의 폭증을 의미합니다.** Agent 10개일 때의 연계 설계와 100개일 때의 설계는 완전히 다릅니다. → **Agent 간 연계 구조(A2A)와 도구 카탈로그 거버넌스가 선택이 아니라 필수**가 됩니다. (`05_Agent간_연계구조_및_기준.md` 참조)

3. **SKT의 "AI 에이전트 사번 부여"는 그대로 벤치마크할 수 있는 그룹 내 선례입니다.** Phase 5 권한 모델 설계 시 외부 사례를 찾기 전에 이것부터 확보하십시오.

## 4. 스마트플랜트 2.0 과제와 본 과업의 관계

기존 40개 과제는 **개별 AI 솔루션**이고, 본 과업은 그것들이 올라탈 **공통 기반**을 설계하는 일입니다.

| 스마트플랜트 2.0 과제 | 필요 Legacy 데이터 | 본 과업이 제공할 것 |
|---|---|---|
| 공정 자동 운전 / 자동 제어 고도화 | **RTDB** 실시간 태그 | 태그↔설비 매핑, 집계 API 요건 |
| **설비 고장예측** | OCEAN-H 정비이력 + RTDB 시계열 | **횡단 식별자(설비↔태그)** — 이 과제의 최대 병목 |
| 통합 안전 모니터링 | RTDB + OCEAN-H + SHE 시스템 | 다중 시스템 연계 구조 |
| 엔지니어링 자료 검색 (Azure GenAI) | 비정형 문서 | ② Knowledge 과업 범위 |

> **설비 고장예측 과제를 Phase 1의 대표 사례로 삼으십시오.** OCEAN-H와 RTDB를 동시에 필요로 하므로 횡단 식별자 문제가 즉시 드러나고, 이미 추진 중이라 담당자와 실제 데이터가 존재합니다. **가장 설득력 있는 근거 사례**가 됩니다.

## 5. 벤치마크: SKT AI 에이전트 거버넌스 `[확인]`

Phase 5(권한) 설계 시 **1순위 참조 대상**입니다.

| 요소 | SKT 방식 | 본 과업 적용 검토 |
|---|---|---|
| 신원 | AI 에이전트에 **사번 부여** | Agent를 권한 주체로 등록 → Service Account 방식(A안)에 가까움 |
| 소속·직무 | **소속과 직무 할당** | Agent에 조직·역할 부여 → 조직 기반 권한 상속 가능 |
| 권한 | **권한 할당**, 데이터·보안 접근 권한 규정 별도 마련 | Phase 5-4 요건의 직접 참조 |
| 생애주기 | **입사~퇴사 유사 절차**로 관리 | Agent 등록·변경·폐기 절차 = Phase 6 변경관리와 연결 |
| 플랫폼 | 사내 AI 개발 플랫폼 통합 + 주요 사내 시스템 연동 | Phase 4 아키텍처 참조 |

**단, 그대로 쓰면 안 되는 지점** — 사번 부여 방식은 Agent 고유 권한(A안)입니다. **OASIS처럼 조직·공정·역할에 권한이 세밀하게 묶인 시스템에서는 최소권한 원칙 위배 문제가 남습니다.** CLX는 **혼합(C안)** — 조회는 사용자 권한 위임, Agent 신원은 사번 기반 — 이 현실적일 가능성이 높습니다. Phase 5-2에서 이 점을 명시적으로 비교하십시오.

### OCEAN-H
4. 15종 통합 당시 **마스터 정비 기준**은 무엇이었고, 산출물이 남아 있습니까?
