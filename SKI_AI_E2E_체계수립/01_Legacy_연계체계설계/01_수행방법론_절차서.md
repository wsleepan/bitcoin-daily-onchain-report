# 수행 방법론 절차서 — ① Legacy 구조 고도화 및 관리체계 설계

기획서 4페이지의 3단계 흐름(`현황 분석 → To-be 방향성 수립 → 실행과제 정의`)을 유지하되,
각 단계를 실행 가능한 Phase로 분해했습니다.

```
Stage 1. 현황 분석 (W1~W6)          Stage 2. To-be 방향성 (W5~W12)         Stage 3. 실행과제 (W11~W14)
 ├ P0 착수·정렬                      ├ P3 데이터·메타 구조 고도화             ├ P7 목표구조·로드맵
 ├ P1 Agent 현황 및 유형 분석         ├ P4 연계 구조 및 적용 기준 ★           └ P8 실행과제·통합보고
 └ P2 Legacy Agent-Readiness 진단    ├ P5 권한 관리체계 고도화
                                     └ P6 Lineage·변경관리 체계
```

---

## Stage 1. 현황 분석

### Phase 0. 착수 · 정렬 (W1)

**목적** — 이후 3.5개월의 판단 기준선 고정. 특히 **1차 범위를 읽기 전용으로 긋는 것**과 **MCP 판단 시점을 뒤로 미루는 것**에 대한 합의.

| # | 활동 | 방법 | 산출 |
|---|---|---|---|
| 0-1 | 범위 기준선 확정 | 대상 Legacy(3종+추가 선정기준), **1차 = 읽기 전용(P-READ~P-MONITOR)** 명문화, 쓰기(P-ACT)는 후속 | 범위 정의서 |
| 0-2 | MCP 논의 정렬 | README 원칙 3의 계층 모델 제시. "MCP 채택 여부는 Phase 4에서 Action Pattern 분석 후 판단" 합의 | 연계방식 판단 기준 합의서 |
| 0-3 | 전사 방침 확보 | 전사 Endpoint/Gateway 표준·API 정책·인증체계 문서 수집, 담당자 접촉 | 전사 방침 자료집 |
| 0-4 | 조사 기반 확보 | 시스템별(OCEAN/OASIS/RTDB) 담당자 지정, 인터뷰·자료 일정 확정 | 조사 계획서 |
| 0-5 | 과업 경계 정의 | ② Knowledge(비정형 문서) / ③ MLOps·AgentOps(Agent 실행·운영)와의 경계 및 인계 항목 합의 | 과업 간 인터페이스 표 |
| 0-6 | 보안 검토 경로 확정 | 권한·감사 설계의 심의 주체·시점 확인 | 보안 검토 계획 |

**완료 판단기준**
- [ ] 1차 범위(읽기 전용) 서면 합의 — 미합의 시 Phase 5 일정이 성립하지 않음
- [ ] MCP 판단 시점 합의 (Phase 4)
- [ ] 시스템별 담당자 지정 및 인터뷰 일정 확정
- [ ] 전사 Endpoint/Gateway 방침 확보 (또는 미확정 사실 확인 + 가정 명시)

> **0-2가 이 과업에서 가장 중요한 합의입니다.** "MCP로 붙이면 되는 것 아니냐"는 기대를 W1에 정리하지 못하면, Phase 2·3의 Legacy 고도화 과제가 "불필요한 일"로 취급됩니다.

### Phase 1. CLX AI Agent 현황 및 유형 분석 (W1 ~ W3)

> 기대산출물: **CLX Brain AI Agent 유형 정의**, **AI Agent 유형별 요구사항 정의**

**목적** — Legacy에 대한 **수요(Demand)** 를 확정한다. 이후 모든 설계의 근거.

**Input** — 추진 중/계획 중 AI Agent 목록, 기획 문서, 담당자

| # | 활동 | 방법 | 산출 |
|---|---|---|---|
| 1-1 | Agent 현황 조사 | 추진 중·계획 중 Agent별 목적 / 역할 / 사용자 / 현재 단계 / **Legacy 활용 범위** 조사 | Agent 현황 목록 |
| 1-2 | 외부 BP 조사 | 제조·화학 도메인 Agent–Legacy 연계 사례, 연계 방식과 실패 요인 | 외부 사례 조사서 |
| 1-3 | **Agent 유형화** | 업무 목적·역할 기준으로 유형 정의 (예: 조회지원형 / 분석형 / 감시형 / 작업지원형 / 실행형) | CLX Brain AI Agent 유형 정의 |
| 1-4 | **Action Pattern 정의** | 유형별로 Legacy에 대해 수행하는 행위를 패턴화 (P-READ / P-SEARCH / P-ANALYZE / P-MONITOR / P-ACT) | Action Pattern 정의서 |
| 1-5 | 유형별 요구사항 도출 | 패턴별 **데이터 / 연계 / 시스템 / 플랫폼** 관점 요구사항. 각 요구는 정량 특성 포함(응답시간·데이터량·갱신주기·권한수준·감사요구) | AI Agent 유형별 요구사항 정의 |
| 1-6 | 수요–시스템 매트릭스 | `Agent 유형 × Legacy 시스템` 으로 어떤 Agent가 어떤 시스템의 무엇을 필요로 하는지 매핑 | 수요 매트릭스 |

**Output** — CLX Brain AI Agent 유형 정의, AI Agent 유형별 요구사항 정의, Action Pattern 정의서, 수요 매트릭스

**완료 판단기준**
- [ ] Agent 유형이 **5~8종 이내**로 수렴 (10종 넘으면 유형화 실패 — 재분류)
- [ ] 모든 유형이 Action Pattern으로 표현되고, 패턴별 **정량 요건**(응답시간·데이터량 등)이 기재됨
- [ ] 수요 매트릭스의 모든 셀이 판정됨 (필요/불요/미정 중 '미정' 0건)
- [ ] **P-ACT(쓰기)에 해당하는 요구가 별도 식별**되어 1차 범위 밖으로 분리됨

> **유형화가 목적이 아닙니다.** 유형은 요구사항을 묶기 위한 수단이며, 최종 산출물은 1-5의 요구사항입니다. 유형 논쟁에 시간을 쓰지 마십시오.

### Phase 2. Legacy Agent-Readiness 진단 (W3 ~ W6)

**목적** — Legacy의 **공급(Supply)** 현황을 공통 축으로 진단하고, 수요와의 Gap을 확정한다.

**Input** — 수요 매트릭스, Action Pattern 정의서, 시스템 문서, 담당자 인터뷰

| # | 활동 | 방법 | 산출 |
|---|---|---|---|
| 2-1 | 시스템 프로파일 조사 | 시스템별 목적·데이터 범위·기술 스택·인터페이스 현황·운영 주체 | Legacy 프로파일 |
| 2-2 | **6축 Readiness 진단** | A1 인터페이스 / A2 데이터 구조 / A3 의미 명확성 / A4 권한 세분성 / A5 관측·감사 / A6 변경관리 각 1~5점 | Agent-Readiness 히트맵 |
| 2-3 | 실제 호출 검증 | 대표 요구 3~5건을 **실제로 조회 시도**. 문서상 API와 실제 동작의 차이 확인 | 검증 기록 |
| 2-4 | Gap 분석 | `Phase 1 수요 요건` vs `2-2 현황` 대비, 시스템×축별 Gap 명세 | Gap 분석서 |
| 2-5 | 추가 대상 시스템 선정 | Phase 0 선정 기준에 따라 3종 외 후보(MES·ERP·LIMS 등) 평가·확정 | 대상 시스템 확정서 |
| 2-6 | 공통/특화 과제 분리 | 3개 이상 시스템에 공통으로 나타나는 Gap = 공통 과제, 나머지 = 시스템 특화 | 과제 후보 목록 |

**Output** — Agent-Readiness 히트맵, Gap 분석서, 대상 시스템 확정서, 과제 후보 목록

**완료 판단기준**
- [ ] 대상 시스템 전부에 대해 6축 점수와 **판정 근거**가 기록됨 (점수만 있으면 무효)
- [ ] 2-3 실제 호출 검증을 최소 3건 수행 (문서만 보고 진단하지 않음)
- [ ] Phase 1 수요 요건의 100%가 Gap 판정을 받음
- [ ] 공통 과제와 시스템 특화 과제가 분리됨

> **2-3(실제 호출 검증)을 생략하지 마십시오.** Legacy 문서와 실제 동작은 거의 항상 다르며, 이 차이가 로드맵의 공수 산정을 좌우합니다. 3건만 해봐도 진단의 신뢰도가 달라집니다.

## Stage 2. To-be 방향성 수립

### Phase 3. Legacy 데이터 · 메타 구조 고도화 방안 (W4 ~ W9)

> 기대산출물: **Agent가 활용하기 용이한 Legacy 데이터 구조 및 메타 요건 정의**, **Agent-ready Data 설계 가이드 및 개선과제**

**목적** — Agent가 **정확하게 해석할 수 있는** 데이터 상태를 정의한다. (6축 중 A2·A3 대응)

| # | 활동 | 방법 | 산출 |
|---|---|---|---|
| 3-1 | Agent-ready Data 요건 정의 | 식별자 체계 / 조회 단위 / 시점 기준(as-of) / 코드 값 의미 / 단위·정밀도 / 결측 표현 | 데이터 구조 요건 |
| 3-2 | **메타·데이터 사전 요건** | 테이블·컬럼·코드값의 **자연어 설명**, 업무 의미, 사용 주의사항. LLM이 읽을 것을 전제로 기술 | 메타 관리 요건 |
| 3-3 | 시스템별 적용 방안 | 시스템별로 3-1·3-2를 어떻게 충족할지 (원천 개선 / 뷰·API 계층 보정 / 별도 매핑 테이블) | 시스템별 적용 방안 |
| 3-4 | 설계 가이드 작성 | 신규 데이터·시스템이 따라야 할 Agent-ready 설계 원칙과 체크리스트 | Agent-ready Data 설계 가이드 |
| 3-5 | 개선과제 도출 | Gap → 과제화, 과제별 영향 범위·난이도·선행조건 | 데이터 영역 개선과제 |

**완료 판단기준**
- [ ] Phase 1 요구사항 중 데이터 관련 항목의 **100%가 요건으로 번역**됨
- [ ] 대표 데이터 대상 3건에 대해 "Agent가 해석 가능한 형태"의 **Before/After 예시** 제시
- [ ] 설계 가이드가 체크리스트 형태로 즉시 적용 가능

> **② Knowledge 과업과의 경계** — 여기서 다루는 것은 **정형 시스템 데이터**입니다. 비정형 문서·지식은 ②의 범위이며, 다만 메타 표준은 상호 참조해 용어·분류가 어긋나지 않게 합니다.

### Phase 4. AI Agent 연계 구조 및 적용 기준 수립 (W6 ~ W11) ★ 핵심

> 기대산출물: **CLX Agent–Legacy 연계 흐름**, **전사 Endpoint/Gateway 반영요건 및 개선과제**

**목적** — 연결 방식을 **선정하고 기준을 세운다.** 이 과업의 Key Question에 대한 직접적 답.

**Input** — Action Pattern 정의서, 수요 매트릭스, Gap 분석서, 전사 방침 자료집

| # | 활동 | 방법 | 산출 |
|---|---|---|---|
| 4-1 | 외부 BP 조사 | Agent–Legacy 연계 아키텍처 사례, MCP 도입 사례의 적용 계층·운영 방식·한계 | 연계 사례 조사서 |
| 4-2 | **연계 방식 후보 정의** | MCP Server / REST·OpenAPI 직접 / GraphQL / 이벤트 스트림 / 배치·복제 / (DB 직접 = 원칙 배제) | 후보 정의서 |
| 4-3 | **Action Pattern × 연계방식 적합성 평가** | 패턴별 지배 요건(실시간성·데이터량·트랜잭션·권한세분성·감사·원천부하)으로 후보 평가 | 적합성 매트릭스 |
| 4-4 | **MCP 채택 판단** | 4-3 결과 + 도입 편익(도구 자율선택·확장성) vs 비용(운영·권한위임·카탈로그 거버넌스) 비교 | MCP 채택 판단서 |
| 4-5 | 연계 아키텍처 설계 | 계층별 역할·경계 정의 (Agent / 도구노출 / Gateway / Legacy API / 데이터). 패턴별 호출 흐름도 | **CLX Agent–Legacy 연계 흐름** |
| 4-6 | 전사 방침 Gap 및 2갈래 산출 | (a) 전사 방침 내에서 CLX가 지켜야 할 **적용 기준** / (b) 전사에 요청할 **개선·협의 사항** | **전사 Endpoint/Gateway 반영요건 및 개선과제** |
| 4-7 | 도구(Tool) 정의 기준 | 도구 단위 분할 원칙, 명명·설명 작성 기준, 입출력 스키마 기준, 도구 카탈로그 관리 R&R | 도구 정의 기준서 |

**Output** — CLX Agent–Legacy 연계 흐름, 전사 Endpoint/Gateway 반영요건 및 개선과제, MCP 채택 판단서, 도구 정의 기준서

**완료 판단기준**
- [ ] **모든 Action Pattern에 연계 방식이 지정**되고 선정 사유가 문서화됨
- [ ] MCP 채택/미채택 결론과 **근거**가 명시됨 (조건부 채택이면 조건 명시)
- [ ] 전사 방침 대비 산출물이 **(a) CLX 적용기준 / (b) 전사 협의사항** 2갈래로 분리됨
- [ ] 대표 시나리오 2건에 대해 **End-to-End 호출 흐름도**(Agent → 도구 → Gateway → Legacy → 응답)가 그려짐
- [ ] 4-5 아키텍처가 Phase 5 권한 모델과 상충하지 않음 (교차 확인)

> **4-3이 이 과업의 지적 중심입니다.** "MCP를 쓸까 API를 쓸까"는 취향이 아니라 **패턴별 요건에 따른 판정**이어야 하며, 하나로 통일할 필요도 없습니다. 실시간 감시는 이벤트 스트림, 탐색적 조회는 MCP, 정형 대량 분석은 배치 복제 — 이렇게 갈리는 것이 정상입니다.

### Phase 5. CLX AI Agent 권한 관리체계 고도화 (W7 ~ W12)

> 기대산출물: **CLX 필요 권한관리 요건**, **권한관리체계 고도화 방안 및 개선과제**

**목적** — "**누구의 권한으로** 접근하는가"에 답한다. 보안 승인의 관문.

| # | 활동 | 방법 | 산출 |
|---|---|---|---|
| 5-1 | 현행 권한 체계 조사 | 시스템별 인증·인가 방식, 권한 단위(행/열/기능), 통합 인증 여부 | 현행 권한 현황 |
| 5-2 | **권한 모델 대안 평가** | A. Agent 고유 권한(Service Account) / B. 사용자 권한 위임(On-Behalf-Of) / C. 혼합 | 권한 모델 비교표 |
| 5-3 | 패턴별 권한 모델 지정 | 조회는 위임(B), 실행은 Agent 권한 + 승인(C) 등 Action Pattern별 적용 | 권한 적용 기준 |
| 5-4 | 권한 요건 정의 | 최소권한, 결과 필터링, 위임 범위·기간, 권한 상승 방지, 다중 Agent 연쇄 호출 시 권한 전파 | **CLX 필요 권한관리 요건** |
| 5-5 | Gap 및 고도화 방안 | 현행 대비 부족분 → 시스템별/공통 고도화 방안 | **권한관리체계 고도화 방안 및 개선과제** |
| 5-6 | 보안 검토 | Phase 0에서 확인한 심의 주체에 사전 리뷰 | 검토 의견 반영 |

**완료 판단기준**
- [ ] 모든 Action Pattern에 권한 모델이 지정됨
- [ ] **결과 필터링 요건**이 명시됨 (Agent가 요청자 권한 밖 데이터를 반환하지 않음)
- [ ] Agent 연쇄 호출(Agent→Agent) 시 권한 전파 규칙이 정의됨
- [ ] 보안 담당 사전 검토 의견 수령 및 반영

> **5-2가 실무의 핵심 난제입니다.** A안은 구현이 쉽지만 최소권한 원칙에 위배되어 보안 승인이 어렵고, B안은 안전하지만 토큰 전파·세션 관리가 복잡합니다. 대부분 C(혼합)으로 수렴하며, **어느 패턴에 무엇을 적용할지**를 문서로 못박는 것이 산출물의 실질입니다.

### Phase 6. CLX AI 구성요소 Lineage 및 변경관리 체계 설계 (W9 ~ W13)

> 기대산출물: **CLX 필요 Lineage 및 변경관리 요건**, **Lineage 및 변경관리체계 고도화 방안 및 개선과제**

**목적** — "무언가 바뀌었을 때 **무엇이 영향받는지** 안다"를 성립시킨다.

| # | 활동 | 방법 | 산출 |
|---|---|---|---|
| 6-1 | **관리 대상 구성요소 식별** | 모델 / 프롬프트 / 도구 정의 / 데이터 소스·스키마 / Agent 구성 / 정책·권한 설정 | 구성요소 목록 |
| 6-2 | Lineage 범위 정의 | 어디부터 어디까지 추적할 것인가 (데이터 원천 → 도구 → Agent → 응답, 응답의 근거 추적 포함) | Lineage 범위 정의 |
| 6-3 | 변경 시나리오 분석 | 각 구성요소가 바뀔 때의 영향 경로 (예: Legacy 스키마 변경 → 도구 정의 → Agent 응답 오류) | 변경 영향 분석 |
| 6-4 | 요건 정의 | 추적 식별자, 버전 관리 단위, 영향 분석 방법, 변경 승인 절차, 하위호환 규칙 | **CLX 필요 Lineage 및 변경관리 요건** |
| 6-5 | Gap 및 고도화 방안 | 현행 대비 부족분 → 고도화 방안·개선과제 | **Lineage 및 변경관리체계 고도화 방안** |
| 6-6 | ③ 과업 정합 확인 | MLOps·AgentOps의 모델·Agent 버전관리와 중복·공백 확인 | 정합 확인서 |

**완료 판단기준**
- [ ] 관리 대상 구성요소가 빠짐없이 식별됨 (**프롬프트·도구 정의 누락이 가장 흔함**)
- [ ] 대표 변경 시나리오 3건의 영향 경로가 End-to-End로 그려짐
- [ ] ③ MLOps/AgentOps 과업과 역할 경계가 합의됨

> **Legacy 스키마 변경이 Agent 응답을 조용히 망가뜨리는 것**이 이 Phase가 막으려는 사고입니다. 전통적 시스템 연계는 오류가 나지만, Agent는 그럴듯한 틀린 답을 반환합니다. 그래서 A6(변경관리)가 6축에 들어가 있습니다.
