# AI Agent 간 연계 구조 및 적용 기준

> 참조 아키텍처 **L5 계층**. Agent–Legacy 연계(L1~L4)를 다룬 다른 문서와 달리, **Agent와 Agent 사이**를 다룹니다.
> 기획서 ① 과업의 "AI Agent 연계 구조 및 적용 기준 수립"을 Agent 간 관점까지 확장한 문서.

---

## 0. 왜 지금 이것을 설계해야 하는가

기획서에는 "AI Agent 연계 구조"가 있지만, 통상 이는 **Agent–Legacy 연계**로만 해석됩니다.
그러나 SK 그룹의 방향이 **'1인 1에이전트'** 이고, 울산CLX에 이미 **스마트플랜트 2.0 과제 40여 개**가 돌아가고 있습니다.

**Agent 수가 늘면 문제의 성격이 바뀝니다.**

| Agent 수 | 지배적 문제 | 필요 설계 |
|---|---|---|
| 1~5개 | Legacy에 어떻게 붙나 | L1~L4 (도구·API) |
| 10~30개 | 도구 중복, 권한 일관성 | 도구 카탈로그 거버넌스 |
| **50개+** | **Agent 간 중복·충돌·연쇄 책임** | **L5 Agent 간 연계 체계** |

> 지금 설계하지 않으면, 2년 뒤 **"Agent 40개가 각자 Legacy에 직접 붙어 있고 아무도 전체를 모르는 상태"** 가 됩니다. 이는 정확히 OCEAN-H 구축 전 **15종 시스템이 난립하던 상황의 재현**입니다. 조직에 그 학습이 남아 있으므로, 이 비유가 가장 잘 통합니다.

## 1. 프로토콜 계층 — MCP와 A2A는 경쟁이 아니다

| | **MCP** (Model Context Protocol) | **A2A** (Agent2Agent) |
|---|---|---|
| 계층 | **Agent ↔ 도구** | **Agent ↔ Agent** |
| 해결 문제 | Agent가 외부 도구·데이터를 발견하고 호출 | Agent가 다른 Agent를 발견하고 작업을 위임·협업 |
| 최신 사양 | 2025-11-25 스펙 (분산 실행, stateless 전송, 보안 프레임워크) | **v1.0 (2026.04 릴리스)** |
| 생태계 | 월 1억 1천만 회 이상 다운로드 | **150+ 조직 지원**, AWS·Microsoft·Google 클라우드 통합 |
| 주요 참여 | — | AWS, Cisco, Google, Microsoft, Salesforce, SAP, ServiceNow |
| 본 과업에서 | Phase 4 (L4) | **본 문서 (L5)** |

**둘의 관계**

```
       ┌──────────┐   A2A   ┌──────────┐
       │ Agent A  │ ←─────→ │ Agent B  │      L5: Agent 간 협업
       └────┬─────┘         └────┬─────┘
            │ MCP                │ MCP           L4: 도구 호출
       ┌────▼─────┐         ┌────▼─────┐
       │ 도구/데이터 │         │ 도구/데이터 │
       └──────────┘         └──────────┘
```

> **핵심 판단** — A2A는 2026년 4월 v1.0이 나온 신생 표준입니다. **지금 채택을 확정할 단계가 아니라, "Agent 간 연계가 필요해질 때 A2A로 갈 수 있도록 구조를 열어두는" 것이 적정 수준**입니다. 본 과업의 산출물은 A2A 구현이 아니라 **Agent 간 연계 기준**입니다.
>
> 다만 표준 거버넌스 연구에서 **MCP·A2A 모두 권한 위임·책임 소재를 충분히 표현하지 못한다**는 지적이 나오고 있으므로, 프로토콜에 의존하지 말고 **조직 차원의 기준을 별도로 세워야 합니다.** 이것이 아래 3~5장입니다.

## 2. Agent 간 연계 패턴

### 2-1. 4가지 기본 패턴

| 패턴 | 구조 | 적합 상황 | CLX 예시 | 리스크 |
|---|---|---|---|---|
| **P1. 단독** | Agent 1개가 도구 다수 호출 | 단일 도메인 질의 | 생산실적 조회 | 없음 (기본형) |
| **P2. 오케스트레이터–워커** | 상위 Agent가 하위 Agent에 위임·취합 | **횡단 질의** | 설비이상 종합 분석 | 상위 Agent 병목, 책임 소재 |
| **P3. 체인** | Agent A 출력 → Agent B 입력 | 단계적 처리 | 이상감지 → 원인분석 → 조치제안 | 오류 전파·증폭 |
| **P4. 피어 협의** | Agent 간 대등한 상호 조회 | 상호 참조 필요 | (현 단계 권장 안 함) | 무한 루프, 추적 불가 |

### 2-2. CLX 적용 권고

> **P2(오케스트레이터–워커)를 기본으로, P3(체인)은 제한적으로, P4(피어)는 1차 범위 제외.**

**근거**
- P2는 **책임 소재가 명확**합니다. 상위 Agent가 최종 답변의 책임을 집니다.
- P4는 추적·디버깅이 급격히 어려워지고, 무한 루프·순환 참조가 발생합니다. 성숙도가 충분해진 뒤에 검토합니다.
- 이 판단은 Legacy 연계의 원칙 2(읽기/쓰기 분리)와 같은 성격입니다 — **통제 가능한 것부터.**

### 2-3. 도메인 Agent 구성안 (CLX)

시스템 경계가 아니라 **업무 도메인 경계**로 Agent를 나눕니다.

| Agent | 담당 도메인 | 주 사용 시스템 | Pattern |
|---|---|---|---|
| **설비 Agent** | 설비 사양·정비이력·유사사례 | OCEAN-H | P-READ, P-SEARCH |
| **공정 Agent** | 실시간·이력 공정값, 추이·편차 | RTDB | P-ANALYZE, P-MONITOR |
| **생산 Agent** | 생산계획·실적·품질 | OASIS | P-READ, P-ANALYZE |
| **지식 Agent** | 기술문서·규정·과거 보고서 | ② Knowledge Hub | P-SEARCH |
| **종합 분석 Agent** (오케스트레이터) | 횡단 질의 조합·판단 | 위 Agent들 (A2A) | — |

> **왜 시스템별이 아니라 도메인별인가** — 시스템은 바뀌지만 업무 도메인은 오래 갑니다. OCEAN-H가 언젠가 교체되어도 "설비 Agent"라는 경계는 유지됩니다. 또한 도메인 담당 조직이 곧 Agent 소유 조직이 되어 R&R이 자연스럽게 정해집니다.

### 2-4. 대표 시나리오 — 횡단 질의의 실제 흐름

> *"3호기 압축기 지난달 트립, 원인이 뭐고 생산에 얼마나 영향 있었나?"*

```
[사용자]
   │
   ▼
[종합 분석 Agent] ── 질의 분해 ──┬─→ [설비 Agent]  "3호기 압축기 트립 이력"
   │                            │        └→ MCP → OCEAN-H
   │                            │        ← 설비ID, 트립 시각, 정비 기록
   │                            │
   │                            ├─→ [공정 Agent]  "해당 설비, 트립 전후 2시간 추이"
   │                            │        └→ 집계 API → RTDB
   │                            │        ← 온도·압력 구간 통계, 임계 초과 시점
   │                            │
   │                            └─→ [생산 Agent]  "해당 시간대 생산 실적"
   │                                     └→ REST+Gateway → OASIS
   │                                     ← 생산일·교대 실적, 계획 대비 차이
   │
   ├─ 취합·판단 (시간축 정렬, 인과 추론)
   ▼
[답변 + 근거 출처 3건]
```

**이 흐름이 성립하기 위한 전제** — 전부 Legacy 연계 쪽 산출물입니다.

| 전제 | 소관 | 없으면 |
|---|---|---|
| "3호기 압축기" → 설비ID | 설비 별칭 사전 (Phase 3) | 시작조차 못 함 |
| 설비ID → 관련 태그 | **태그 매핑** (Phase 3) | 공정 Agent 호출 불가 |
| 트립 시각 → 생산일·교대 | 시간축 변환 (Phase 3) | 생산 실적을 못 찾음 |
| 사용자 권한이 3개 Agent에 전파 | **권한 전파** (Phase 5 + 본 문서 4장) | 권한 밖 데이터 노출 |

> **L5 설계는 L1~L4가 없으면 그림에 불과합니다.** 이 표를 착수보고에 넣으면 "왜 Legacy 고도화가 먼저인가"가 한 장으로 설명됩니다.

## 3. Agent 간 계약(Contract) 기준

Agent가 다른 Agent를 호출한다는 것은 **API 호출이 아니라 업무 위임**입니다. 계약이 필요합니다.

### 3-1. Agent 카드 (등록 명세)

```
Agent ID:      AGT-EQP-001
Agent 명:      설비 Agent
소유 조직:      EAM 운영
Agent 신원:     사번 기반 (SKT AX 혁신 2.0 방식 참조)
담당 도메인:    설비 사양, 정비 이력, 유사 사례 탐색
할 수 있는 것:  - 설비 식별(현장 호칭 → 설비ID)
               - 설비 기본정보·계층 조회
               - 정비 이력 조회 및 유사 사례 검색
할 수 없는 것:  - 실시간 공정값 (→ 공정 Agent)
               - 생산 실적 (→ 생산 Agent)
               - 작업오더 생성 등 쓰기 (1차 범위 밖)
사용 도구:      OCEANH_* (7개)
입력 계약:      {질의: string, 설비ID?: string, 기간?: {시작, 종료}, 사용자컨텍스트: token}
출력 계약:      {답변: string, 근거: [{출처, 도구ID, 조회시각, 정제상태}], 신뢰도: enum}
권한:          요청 사용자 권한 상속 (위임). 협력사 정보 마스킹.
응답 목표:      P-READ 5초 / P-SEARCH 15초
실패 시:        부분 결과 + 실패 범위 명시. 추정 금지.
소유자 연락:    OOO
등록/변경:      2026-XX-XX / v1.2
```

**필수 항목 중 가장 중요한 것: `할 수 없는 것`**
오케스트레이터가 어느 Agent에 위임할지 판단하는 근거입니다. 이것이 없으면 잘못된 Agent에 위임하고, 그 Agent는 **모른다고 하지 않고 추측해서 답합니다.**

### 3-2. 응답 계약 — 근거 필수

Agent 간 응답에는 **반드시 근거(Provenance)가 동반**되어야 합니다.

| 필드 | 내용 | 이유 |
|---|---|---|
| 출처 시스템·도구ID | 어느 도구로 가져왔나 | 오류 추적 |
| 조회 시각 | 언제 기준 데이터인가 | 최신성 판단 |
| **정제 상태** | 검증완료 / 미검증 | **OCEAN-H 미정제 20% 대응** |
| 신뢰도 | 확실 / 추정 / 불충분 | 상위 Agent의 판단 근거 |
| 미확보 범위 | 못 가져온 부분 | 상위 Agent가 "없다"와 "못 봤다"를 구분 |

> **"불충분"을 반환할 수 있어야 합니다.** Agent가 항상 답을 내도록 설계하면 없는 사실을 만들어냅니다. **모른다고 말할 수 있는 것이 계약의 핵심 조항**입니다.

## 4. Agent 간 권한 전파 ★ 최대 난제

Phase 5(권한)의 연장선이며, Agent 간 연계에서 가장 위험한 지점입니다.

### 4-1. 문제

```
사용자(A공장 권한) → 종합 Agent → 설비 Agent → OCEAN-H
                              └→ 생산 Agent → OASIS (B공장 데이터 접근?)
```

중간 Agent가 자기 권한으로 조회하면, **사용자가 볼 수 없는 데이터가 답변에 섞여 나옵니다.** 사용자는 그것이 권한 밖 데이터인지 알 수 없습니다.

### 4-2. 전파 원칙

| # | 원칙 | 내용 |
|---|---|---|
| **A1** | **최소 권한 승계** | 하위 Agent의 유효 권한 = `min(사용자 권한, Agent 권한)`. 절대 확대되지 않음 |
| **A2** | 사용자 컨텍스트 필수 전파 | 모든 Agent 간 호출에 요청자 신원·권한 컨텍스트 동반. 익명 호출 금지 |
| **A3** | 전파 깊이 제한 | 위임 체인 최대 깊이 지정 (권장 3). 초과 시 차단 |
| **A4** | 권한 밖 명시 | 권한으로 제외된 데이터가 있으면 **"일부 결과가 권한으로 제외됨"** 을 응답에 표시 |
| **A5** | 감사 이중 기록 | 최종 사용자 + 호출 Agent 체인 전체를 로그에 기록 |
| **A6** | 쓰기 위임 금지 | Agent가 다른 Agent에 **쓰기 작업을 위임할 수 없음** (1차 범위에서는 쓰기 자체가 없음) |

> **A4가 실무에서 가장 자주 빠집니다.** 권한으로 필터링된 결과를 그대로 반환하면 사용자는 "데이터가 없다"고 이해합니다. 안전사고 원인 분석에서 이는 치명적입니다.

### 4-3. Agent 신원 체계 — SKT 사례 적용

SKT의 **AI 에이전트 사번 부여**(AX 혁신 2.0)는 그룹 내 선례로 직접 참조 가능합니다.

| 요소 | SKT 방식 | CLX 적용 검토 |
|---|---|---|
| 신원 | 사번 부여 | ○ 채택 — Agent를 권한 주체로 등록 |
| 소속·직무 | 조직·직무 할당 | ○ 채택 — 도메인 Agent를 소유 조직에 배속 |
| 권한 | 권한 할당 + 데이터·보안 접근 규정 | **△ 보완 필요** — Agent 고유 권한만으로는 OASIS 같은 세분 권한 시스템에서 최소권한 위배 |
| 생애주기 | 입사~퇴사 유사 절차 | ○ 채택 — 등록·변경·폐기 절차 |

**CLX 권고: 혼합 모델**
- **신원**은 사번 기반 (SKT 방식) — 감사·거버넌스에 유리
- **권한**은 사용자 위임 우선 (OBO) — 조회 시 사용자 권한으로 필터링
- Agent 고유 권한은 **사용자 무관 배치 작업**(정기 감시 등)에만 한정

## 5. Agent 간 연계 적용 기준 (산출물 양식)

| 영역 | 기준 |
|---|---|
| **연계 허용 조건** | Agent 카드 등록 완료 + 소유 조직 지정 + 권한 모델 승인 |
| **패턴 제한** | P2(오케스트레이터–워커) 기본. P3(체인) 최대 3단계. **P4(피어) 금지** |
| **위임 깊이** | 최대 3. 초과 호출 차단 |
| **순환 방지** | 호출 체인에 동일 Agent 재등장 금지 |
| **권한** | 4-2 A1~A6 전부 준수 |
| **응답** | 근거(Provenance) 필수. "불충분" 반환 허용 |
| **타임아웃** | 상위 Agent가 하위에 타임아웃 지정. 초과 시 부분 결과로 진행 |
| **실패 처리** | 하위 실패 시 상위는 **실패 사실을 답변에 명시**. 추정 대체 금지 |
| **감사** | 전체 체인 로깅. 최종 사용자 식별 필수 |
| **도메인 경계** | Agent는 자기 도메인 밖 데이터를 직접 조회하지 않고 담당 Agent에 위임 |
| **중복 방지** | 신규 Agent 등록 시 기존 Agent와 도메인 중복 검토 필수 |

## 6. 거버넌스 — Agent 카탈로그

도구 카탈로그(L4)와 별개로 **Agent 카탈로그(L5)** 가 필요합니다.

| 항목 | 규칙 |
|---|---|
| 등록 | Agent 카드 작성 + 소유 조직 지정 + 도메인 중복 검토 |
| 도메인 배정 | 도메인당 주 담당 Agent 1개 원칙 (난립 방지) |
| 변경 | `할 수 있는 것/없는 것` 변경 시 의존 Agent에 통보 |
| 폐기 | 의존 Agent 확인 후 예고 |
| 모니터링 | 위임 성공률, 오위임률, 체인 깊이 분포, "불충분" 반환율 |
| 정기 점검 | 반기 1회 — 도메인 중복, 미사용 Agent, 권한 적정성 |

**③ MLOps/AgentOps 과업과의 경계**

| 항목 | ① 본 과업 | ③ MLOps·AgentOps |
|---|---|---|
| Agent 간 연계 **구조·기준** | ● | — |
| Agent 카드 **양식·등록 기준** | ● | — |
| 권한 전파 **원칙** | ● | — |
| Agent **실행·배포·버전관리** | — | ● |
| **런타임 모니터링·장애 대응** | — | ● |
| Agent 카탈로그 **시스템 운영** | 요건 정의 | ● 구축·운영 |

> 경계 원칙: **①은 "어떤 규칙으로 연결되는가", ③은 "그것을 어떻게 돌리고 지키는가".**
> W11~W12에 인계 회의를 배치하고, Agent 카드 양식과 권한 전파 원칙을 ③의 운영 요건으로 넘깁니다.
