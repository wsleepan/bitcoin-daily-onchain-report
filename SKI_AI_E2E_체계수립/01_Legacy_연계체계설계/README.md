## 2. 이 과업의 핵심 구조 — 무엇이 진짜 문제인가

"AI와 Legacy를 어떻게 연결할 것인가"는 **하나의 질문이 아니라 다섯 개의 질문**입니다.
이를 섞어서 다루면 결론이 나오지 않습니다. 방법론은 이 다섯을 분리해 순서대로 답합니다.

| # | 질문 | 성격 | 담당 Phase |
|---|---|---|---|
| Q1 | Agent는 Legacy에 **무엇을** 요구하는가 | 수요 정의 | Phase 1 |
| Q2 | Legacy는 지금 **얼마나 준비되어 있는가** | 현황 진단 | Phase 2 |
| Q3 | **어떤 방식으로** 연결할 것인가 (MCP / API / Gateway) | 연계 설계 ★ | Phase 4 |
| Q4 | **누구의 권한으로** 접근하는가 | 권한 설계 | Phase 5 |
| Q5 | 바뀌었을 때 **무엇이 영향받는지** 아는가 | 변경 관리 | Phase 6 |

> Q3(연계 방식)만 논의하면 반드시 막힙니다. Q1이 없으면 선정 기준이 없고, Q2가 없으면 무엇을 고쳐야 하는지 모르며, Q4가 없으면 보안 승인을 못 받습니다.

## 3. 5대 설계 원칙

### 원칙 1. Action Pattern이 연계 요건을 결정한다 (Agent-Backward)
연계 방식을 먼저 고르고 Agent를 맞추면 반드시 재작업이 발생합니다.
`Agent 유형 → Action Pattern → 인터페이스 특성 요건 → 연계 방식` 순으로 역산합니다.

**Action Pattern 분류 (예시)**

| Pattern | 설명 | 지배적 요건 |
|---|---|---|
| P-READ | 정형 데이터 조회 | 응답속도, 권한 필터링 |
| P-SEARCH | 탐색적 검색·문서 조회 | 의미 이해, 관련성 |
| P-ANALYZE | 대량 이력 분석·집계 | 데이터량, 원천 부하 |
| P-MONITOR | 실시간 상태 감시 | 실시간성, 이벤트 |
| P-ACT | 시스템에 쓰기·실행 | **승인, 감사, 롤백** |

### 원칙 2. 읽기와 쓰기는 완전히 다른 문제다 (Read/Write 분리)
`P-READ ~ P-MONITOR`는 **데이터 구조·검색성** 문제이고,
`P-ACT`는 **권한·감사·롤백** 문제입니다. 난이도와 리스크가 자릿수 단위로 다릅니다.

→ **1차 범위는 읽기 전용(P-READ~P-MONITOR)으로 고정**하고, 쓰기는 별도 게이트(승인 워크플로·영향범위 한정·롤백 절차)를 갖춘 후속 단계로 분리합니다. 이 선을 긋지 않으면 보안·현업 검토에서 전체가 멈춥니다.

### 원칙 3. MCP는 배관이 아니라 어댑터다 (계층 분리)
이 과업 최대의 오해 지점입니다. **MCP를 도입한다고 Legacy가 Agent-ready가 되지 않습니다.**

```
 [AI Agent]
     ↓  도구 발견·호출 규약          ← MCP는 여기
 [도구 노출 계층: MCP Server / Tool Adapter]
     ↓  인증 · 인가 · 감사
 [전사 Endpoint / API Gateway]        ← 전사 방침 종속
     ↓
 [Legacy API 계층]  (OCEAN / OASIS / RTDB)   ← 여기가 없으면 위가 무의미
     ↓
 [Legacy 데이터 · 메타 계층]                   ← 여기가 부실하면 답이 틀림
```

- MCP 채택 여부와 **무관하게** 하위 2개 계층(Legacy API, 데이터·메타)의 고도화는 필요합니다.
- MCP의 실익은 *도구 설명·스키마 표준화 → Agent의 자율적 도구 선택, 도구 추가 시 Agent 재개발 불필요*.
- MCP의 비용은 *서버 운영, 권한 위임 설계, 도구 카탈로그 거버넌스*.
- 따라서 **MCP 채택 판단은 Phase 4에서 Action Pattern 분석 이후**에 내립니다. 지금 미리 정하지 않는 것이 맞습니다.

### 원칙 4. 전사 방침에 종속하고, CLX는 적용 기준만 만든다
기대산출물에 "**전사 Endpoint/Gateway 반영요건 및 개선과제**"가 명시되어 있습니다.
CLX가 독자 연계 경로를 설계하면 전사 거버넌스와 충돌하고 중복 투자 지적을 받습니다.

→ `전사 방침 확인 → CLX 요건과의 Gap 식별 → (a) CLX 적용 기준 도출 / (b) 전사 개선 요청사항 도출` 로 산출물을 **2갈래로 분리**합니다. 이 구분이 기획서의 "전사 공통/협의사안 vs. CLX 특화 과제"(4페이지)에 정확히 대응합니다.

### 원칙 5. 진단은 시스템별이 아니라 공통 축으로 (Agent-Readiness 6축)
OCEAN·OASIS·RTDB를 각각 개별 진단하면 시스템별 개선 목록만 나오고 **통합 로드맵이 나오지 않습니다.**
동일한 6축으로 평가해 히트맵을 만들면, 공통 과제와 시스템 특화 과제가 자동으로 갈립니다.

| 축 | 평가 내용 | 미흡 시 증상 |
|---|---|---|
| A1 인터페이스 | API 존재·문서화·표준(OpenAPI) 준수 | Agent가 호출할 수단이 없음 |
| A2 데이터 구조 | 식별자 체계, 정규화, 조회 효율 | 원하는 단위로 못 꺼냄 |
| A3 **의미 명확성** | 컬럼·코드의 의미가 기계/LLM에 설명 가능한가 (데이터 사전·메타) | **Agent가 잘못 해석해 틀린 답을 함** |
| A4 권한 세분성 | 행·열 수준 통제, 위임 가능 여부 | 전부 열거나 전부 막는 선택뿐 |
| A5 관측·감사 | 호출 로그, 추적 ID, 접근 이력 | 사고 시 추적 불가, 보안 승인 불가 |
| A6 변경 관리 | 스키마 버전, 영향 분석, 하위호환 | 조용히 깨짐 |

> **A3(의미 명확성)이 가장 과소평가되는 축입니다.** API가 있어도 `STS_CD = '03'`이 무슨 뜻인지 Agent가 모르면 답이 틀립니다. 전통적 시스템 연계에는 없던 요건이며, 이 과업이 단순 API 개발과 다른 지점입니다.

## 5. 핵심 리스크

| # | 리스크 | 왜 위험한가 | 대응 |
|---|---|---|---|
| R1 | **MCP를 "배관"으로 오해** | MCP만 얹으면 된다는 기대 → Legacy 고도화 과제가 부정됨 | 원칙 3 계층 모델을 착수보고에 명시, MCP 판단을 Phase 4로 명문화 |
| R2 | **Legacy 소유 조직 협조 미확보** | OCEAN·OASIS·RTDB 담당이 각각 다름. 진단 자체가 불가 | 착수 전 시스템별 담당자 지정 및 인터뷰·자료 일정 확보 |
| R3 | **전사 Gateway 방침 미확정** | CLX 적용 기준을 만들 근거가 없음 | Phase 0에서 방침 확인. 미확정이면 가정을 명시하고 시나리오 2안으로 진행 |
| R4 | **권한 위임 설계 누락** | Agent가 사용자 권한을 넘어선 데이터를 노출 → 보안 승인 반려 | Phase 5를 독립 Phase로 배치, 조회 필터링을 필수 요건화 |
| R5 | **쓰기(P-ACT) 범위 팽창** | "Agent가 작업지시까지 내리면 좋겠다" → 승인·감사 설계로 일정 붕괴 | 원칙 2, 1차 읽기 전용을 범위 기준선에 명문화 |
| R6 | **대상 시스템 확산** | 3종 + 추가 후보가 5~6종으로 늘어남 | Phase 0에서 선정 기준·우선순위 확정, 추가분은 "확장 가이드"로 이관 |
| R7 | **② Knowledge 과업과 경계 모호** | 같은 데이터를 두 과업이 중복 설계 | 경계 규칙: **정형 시스템 데이터 = ①**, **비정형 문서·지식 = ②**. 접점(메타 표준)은 ①의 데이터 사전과 ②의 메타 표준을 상호 참조 |
| R8 | **A3(의미 명확성) 과소평가** | API는 되는데 Agent 답이 틀림 → 프로젝트 신뢰 상실 | 6축 진단에 필수 포함, Phase 3 산출물에 데이터 사전 요건 명시 |
