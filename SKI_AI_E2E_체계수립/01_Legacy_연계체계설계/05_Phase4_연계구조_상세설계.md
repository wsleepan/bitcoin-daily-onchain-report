## 1. 참조 아키텍처 — 5계층 모델

연계 설계에서 벌어지는 대부분의 혼선은 **서로 다른 계층의 문제를 같은 자리에서 논쟁**하기 때문입니다.
계층을 먼저 고정하면 각 결정이 어디에 속하는지 명확해집니다.

```
┌─────────────────────────────────────────────────────────┐
│ L5  Agent 계층        업무 Agent (고장예측·운전지원·안전감시)  │
│                       ↕ A2A (Agent 간 협업)                │
├─────────────────────────────────────────────────────────┤
│ L4  도구 노출 계층     MCP Server / Tool Adapter            │  ← MCP는 여기
│                       도구 카탈로그 · 스키마 · 설명           │
├─────────────────────────────────────────────────────────┤
│ L3  통제 계층         전사 Endpoint / API Gateway           │  ← 전사 방침 종속
│                       인증 · 인가 · 레이트리밋 · 감사로그      │
├─────────────────────────────────────────────────────────┤
│ L2  의미 계층         데이터 사전 · 코드 사전 · 태그 매핑       │  ★ 가장 과소평가
│                       횡단 식별자 매핑 (설비·시간·공정·오더)    │
├─────────────────────────────────────────────────────────┤
│ L1  원천 계층         OASIS · OCEAN-H · RTDB               │
│                       Legacy API / 데이터 구조               │
└─────────────────────────────────────────────────────────┘
```

**계층별 결정 사항과 소관**

| 계층 | 핵심 결정 | Phase | 결정 주체 |
|---|---|---|---|
| L5 | Agent 간 협업 구조, 오케스트레이션 | 별도 문서 `05_Agent간_연계구조` | ①(구조) + ③(운영) |
| L4 | **MCP 채택 여부**, 도구 분할 단위, 도구 카탈로그 거버넌스 | **Phase 4** | ① |
| L3 | 인증·인가 방식, 레이트리밋, 감사 요건 | Phase 4 + Phase 5 | 전사 IT + ① |
| L2 | 식별자 표준, 데이터·코드 사전 | **Phase 3** | ① |
| L1 | Legacy API 신설·개선, 데이터 구조 개선 | Phase 3 + Phase 7 | 각 시스템 담당 |

> **핵심 원칙 — 위에서 아래로 설계하고, 아래에서 위로 구축합니다.**
> 설계는 L5(Agent가 뭘 원하나)에서 시작해 내려오고, 구축은 L1·L2(원천·의미)부터 올라갑니다.
> L4(MCP)부터 만들면 아래가 비어 있어 동작하지 않습니다.

## 2. Action Pattern × 연계 방식 적합성 평가 (4-3 상세)

### 2-1. Action Pattern 정의 (CLX 구체화)

| Pattern | 정의 | CLX 예시 | 대표 시스템 |
|---|---|---|---|
| **P-READ** | 식별된 대상의 정형 데이터 조회 | "3호기 압축기 사양", "오늘 생산실적" | OCEAN-H, OASIS |
| **P-SEARCH** | 조건이 모호한 탐색적 검색 | "유사 트립 사례 찾아줘" | OCEAN-H (정비이력) |
| **P-ANALYZE** | 대량 데이터 집계·비교 | "지난달 온도 추이, 정상 대비 편차" | RTDB, OASIS |
| **P-MONITOR** | 상태 변화 감시·알림 | "임계치 초과 시 알림" | RTDB |
| **P-ACT** | 시스템에 쓰기·실행 | "작업오더 생성", "실적 입력" | OASIS, OCEAN-H |

### 2-2. 패턴별 지배 요건

| Pattern | 응답시간 | 데이터량 | 호출빈도 | 권한세분성 | 감사요구 | 원천부하 |
|---|---|---|---|---|---|---|
| P-READ | **초** | 소 | 고 | 고 | 중 | 저 |
| P-SEARCH | 초~십초 | 중 | 중 | 중 | 중 | 중 |
| P-ANALYZE | 십초~분 | **대** | 저 | 중 | 중 | **고** |
| P-MONITOR | **실시간** | 소(연속) | **상시** | 중 | 저 | 중 |
| P-ACT | 초 | 소 | 저 | **최고** | **최고** | 저 |

### 2-3. 연계 방식 후보

| 방식 | 성격 | 강점 | 약점 |
|---|---|---|---|
| **MCP Server** | 도구 노출 규약 | 스키마+설명 내장, Agent 자율 도구 선택, 도구 추가 시 Agent 무수정 | 서버 운영, 권한 위임 설계 필요, 대량 데이터 부적합 |
| **REST / OpenAPI 직접** | 표준 API 호출 | 성숙, Gateway 통합 용이, 권한·감사 체계 활용 | 도구 설명이 Agent 밖에 있어 프롬프트 부담, 호출 경로 고정 |
| **GraphQL** | 유연 조회 | over-fetching 방지, 복합 조회 1회 | 도입 비용, Legacy 적용 난이도 |
| **이벤트 스트림** | 발행–구독 | 실시간, 원천 부하 낮음 | 조회 불가(푸시 전용), 인프라 필요 |
| **배치·복제** | 분석용 사본 | 대량 처리, 원천 부하 0 | 최신성 지연, 저장소 비용 |
| ~~DB 직접 접근~~ | — | (최단 경로) | **원칙적 배제** — 권한 통제·변경 추적 불가 |

### 2-4. 적합성 매트릭스 (판정 결과 — Phase 2 진단으로 검증)

`◎ 최적 / ○ 적합 / △ 조건부 / × 부적합`

| Pattern | MCP | REST | GraphQL | 이벤트 | 배치·복제 |
|---|---|---|---|---|---|
| P-READ | ○ | **◎** | ○ | × | △ |
| **P-SEARCH** | **◎** | △ | ○ | × | ○ |
| **P-ANALYZE** | △ | △ | △ | × | **◎** |
| **P-MONITOR** | × | × | × | **◎** | × |
| P-ACT | △ | **◎** | × | × | × |

**판정 근거**
- `P-SEARCH → MCP ◎` — 검색은 **어떤 도구를 쓸지 Agent가 판단**해야 합니다. 도구 설명이 규약에 내장된 MCP의 실익이 가장 큽니다.
- `P-ANALYZE → 배치·복제 ◎` — 대량 집계를 실시간 API로 하면 원천이 죽습니다. RTDB 1개월 조회가 대표적.
- `P-MONITOR → 이벤트 ◎` — 요청–응답 모델로는 상시 감시가 성립하지 않습니다. 폴링은 부하만 만듭니다.
- `P-ACT → REST ◎` — 쓰기는 Gateway의 인증·인가·감사를 반드시 통과해야 하며, 이 체계가 가장 성숙한 것이 REST입니다. MCP는 `△`(권한 위임 설계가 추가로 필요).

## 3. MCP 채택 판단 (4-4 상세)

### 3-1. MCP를 정확히 위치시키기

| 오해 | 사실 |
|---|---|
| "MCP를 도입하면 Legacy가 연결된다" | MCP는 **L4 도구 노출 규약**. L1(Legacy API)·L2(의미)가 없으면 감쌀 대상이 없음 |
| "MCP vs API 중 하나를 고른다" | MCP는 대개 **REST API 위의 어댑터**. 대립이 아니라 계층 관계 |
| "MCP를 쓰면 전사 Gateway를 우회한다" | 우회하면 안 됨. MCP Server가 **Gateway를 호출**하는 구조여야 함 |
| "전부 MCP로 통일해야 한다" | 패턴별로 갈리는 것이 정상 (2-4 매트릭스) |

### 3-2. 채택 판단 의사결정 트리

```
Q1. 해당 영역의 도구(조회 기능)가 5개 이상이고 앞으로 늘어날 것인가?
    ├ No  → REST 직접 호출로 충분. MCP 불요
    └ Yes ↓
Q2. Agent가 상황에 따라 어떤 도구를 쓸지 스스로 판단해야 하는가?
    ├ No (호출 경로 고정) → REST 직접 호출
    └ Yes ↓
Q3. 반환 데이터가 Agent 컨텍스트에 들어갈 크기인가? (수천 행 이하)
    ├ No (대량) → 배치·복제 + 집계 API. MCP 부적합
    └ Yes ↓
Q4. 권한 위임(사용자 컨텍스트 전달) 설계가 가능한가?
    ├ No  → 조건부 보류. Phase 5 권한 모델 확정 후 재판정
    └ Yes → ★ MCP 채택
```

### 3-3. CLX 적용 예상 판정

| 영역 | Q1 | Q2 | Q3 | Q4 | 판정 |
|---|---|---|---|---|---|
| **OCEAN-H 설비·정비이력 탐색** | Yes (설비조회·이력검색·계층탐색·스펙조회·유사사례 등 다수) | **Yes** | Yes | 검증 필요 | **★ MCP 채택 유력** |
| OASIS 실적·계획 조회 | Yes | 부분 | Yes | **위임 필수** | 조건부 — Gateway 우선, MCP는 2단계 |
| OASIS 쓰기 (작업지시 등) | — | — | — | — | **1차 범위 밖** |
| RTDB 대량 집계 | No (집계 API 소수) | No | **No (대량)** | — | **MCP 부적합** — 집계 API + 복제 |
| RTDB 실시간 감시 | — | — | — | — | **이벤트 구독** |

> **예상 결론: "OCEAN-H 중심 부분 채택"**
> 전면 채택도 전면 배제도 아닙니다. 이 결론을 **근거와 함께** 제시하는 것이 4-4의 산출물이며,
> "MCP 도입 여부"를 이분법으로 묻는 질문 자체를 재구성하는 것이 컨설턴트의 역할입니다.

### 3-4. MCP 채택 시 추가 설계 항목

| 항목 | 내용 | 참조 |
|---|---|---|
| 인증 | MCP 최신 스펙(2025-11-25)의 **issuer validation, issuer-bound client credentials, CIMD** 반영 | MCP 로드맵 |
| 권한 위임 | 사용자 컨텍스트를 MCP Server → Gateway → Legacy로 전파하는 방식 | Phase 5 |
| 도구 카탈로그 | 도구 등록·변경·폐기 절차, 소유자 지정 | 4-7 |
| Gateway 관계 | MCP Server는 Gateway를 **우회하지 않고 경유** | L3 |
| 버전·호환 | 도구 스키마 변경 시 하위호환 정책 | Phase 6 |

## 4. 도구(Tool) 설계 기준 (4-7 상세)

MCP 채택 여부와 무관하게, Agent에게 노출하는 모든 기능에 적용되는 기준입니다.

### 4-1. 도구 분할 원칙

| 원칙 | 내용 | 나쁜 예 | 좋은 예 |
|---|---|---|---|
| **업무 단위 분할** | 시스템 테이블이 아니라 업무 질문 단위로 자름 | `select_equipment_master` | `설비_기본정보_조회` |
| **단일 목적** | 하나의 도구는 하나의 질문에만 답함 | `설비_통합조회(옵션 12개)` | `설비_조회` / `정비이력_조회` 분리 |
| **파라미터 최소** | 필수 파라미터 3개 이하 지향 | 필수 8개 | 필수 2 + 선택 4 |
| **결과 크기 제한** | 기본 반환 행수 상한 + 페이징 | 무제한 반환 | 기본 50행 + `next_cursor` |
| **읽기·쓰기 분리** | 한 도구가 조회와 변경을 겸하지 않음 | `설비정보_조회수정` | 분리 |

**분할 단위 판정 기준** — *"현업이 한 문장으로 물어볼 수 있는가"*
"3호기 압축기 최근 정비 이력 알려줘" → 도구 1개. 여기에 "그리고 그때 공정값도" 가 붙으면 **도구 2개 + Agent 조합**입니다.

### 4-2. 도구 명세 표준 (양식)

```yaml
도구ID:        OCEANH_MAINT_HISTORY_001
도구명:        설비_정비이력_조회
소유:          EAM 운영 조직
설명(Agent용): |
  특정 설비의 정비 이력을 조회한다. 예방정비·고장정비·개선작업을 모두 포함한다.
  설비는 설비ID로 지정하며, 현장 호칭(예: "3호기 압축기")으로는 조회할 수 없다.
  → 현장 호칭으로 시작할 때는 `설비_검색` 도구로 설비ID를 먼저 확정할 것.
  기간을 지정하지 않으면 최근 1년을 반환한다. 최대 200건.
입력:
  설비ID:   {type: string, required: true,  desc: "OCEAN-H 설비 마스터 ID", 예: "EQ-U3-C-0012"}
  시작일:   {type: date,   required: false, desc: "미지정 시 1년 전"}
  종료일:   {type: date,   required: false}
  정비유형: {type: enum,   required: false, values: [예방, 고장, 개선], desc: "미지정 시 전체"}
출력:
  건수, 이력목록[{정비일자, 정비유형, 현상, 조치내용, 담당, 협력사여부}]
  ※ 조치내용은 자유서술 텍스트 (② Knowledge 구조화 대상과 중복 — 경계 확인)
권한:        요청 사용자의 설비 열람 권한 상속. 협력사 인원 정보는 마스킹.
Pattern:     P-READ
연계방식:    MCP (OCEAN-H)
오류:        설비ID 미존재 시 유사 설비 후보 3건 제시
변경관리:    스키마 변경 시 30일 전 공지, 하위호환 1버전 유지
```

### 4-3. 도구 설명(Description) 작성 규칙 — 가장 중요

Agent는 **설명만 읽고** 도구를 고릅니다. 설명이 부실하면 잘못된 도구를 호출하거나, 맞는 도구를 못 찾습니다.

| 규칙 | 이유 |
|---|---|
| **무엇을 반환하는지** 명시 | Agent가 목적에 맞는지 판단 |
| **무엇을 반환하지 않는지** 명시 | 오호출 방지 (예: "실시간 값은 포함하지 않음") |
| **선행 도구가 있으면 명시** | 예: "설비ID가 필요하므로 `설비_검색` 을 먼저 호출" |
| **기본값·상한 명시** | Agent가 페이징 필요 여부 판단 |
| **업무 용어로 기술** | 테이블·컬럼명이 아니라 현장 언어 |
| **주의사항 명시** | 예: "정비이력은 협력사 작업이 누락될 수 있음" |

> **도구 설명은 개발 산출물이 아니라 업무 지식 산출물입니다.** IT가 아니라 **현업+컨설턴트가 작성**해야 하며, 이것이 L2(의미 계층)와 직결됩니다.

### 4-4. 도구 카탈로그 거버넌스

'1인 1에이전트' 방향에서 도구 수는 수백 개로 늘어납니다. 처음부터 관리 체계가 필요합니다.

| 항목 | 규칙 |
|---|---|
| 등록 | 소유 조직 지정 필수. 설명·스키마 리뷰 통과 후 등록 |
| 명명 | `{시스템}_{대상}_{행위}` 체계, 한글 도구명 + 영문 ID |
| 중복 방지 | 유사 도구 사전 검색 의무. 중복 시 통합 또는 사유 기재 |
| 변경 | 하위호환 변경은 통보, 비호환 변경은 신버전 병행 + 폐기 예고 |
| 폐기 | 사용 이력 확인 후 90일 예고 |
| 품질 | 호출 실패율·오호출률 모니터링, 임계 초과 시 설명 재작성 |

## 5. 시스템별 연계 설계 (검증 대상)

### 5-1. OCEAN-H (설비관리)

| 항목 | 설계 |
|---|---|
| 주 Pattern | P-READ, **P-SEARCH** |
| 연계 방식 | **MCP Server** (+ 하위 REST API) |
| 필요 도구(예상) | 설비_검색 / 설비_기본정보_조회 / 설비_계층_탐색 / 정비이력_조회 / 유사정비사례_검색 / 작업오더_조회 / 스페어_조회 |
| 선행 과제 | ① 현장 호칭 ↔ 설비ID 매핑(`설비_검색` 의 품질을 좌우) ② 정제 미완료 20% 구간 식별 |
| 특이사항 | **OCEAN-P 협력사 데이터** — 협력사 인원 정보 마스킹 규칙 필요 |
| 검증 포인트 | 자체 개발 시스템이므로 **API 신설 가능성·소요**를 Phase 2에서 확인 (PTC 스택 연동 API 존재 여부 포함) |

> `설비_검색` 도구가 OCEAN-H 연계의 **관문**입니다. 60만 기 설비에서 "3호기 압축기"를 특정하지 못하면 나머지 도구가 전부 무용지물입니다. **이 도구 하나에 설계 공수를 집중**하십시오.

### 5-2. OASIS (생산관리)

| 항목 | 설계 |
|---|---|
| 주 Pattern | P-READ, P-ANALYZE (P-ACT는 1차 범위 밖) |
| 연계 방식 | **REST/OpenAPI + 전사 Gateway** (MCP는 2단계 검토) |
| 필요 도구(예상) | 생산실적_조회 / 생산계획_조회 / 오더_조회 / 품질이력_조회 |
| 선행 과제 | ① **업무 상태 코드 사전** ② **생산일·교대 정의 → 절대시각 변환 규칙** |
| 특이사항 | 권한이 조직·공장·공정·역할에 묶임 → **사용자 권한 위임(OBO) 필수** |
| 검증 포인트 | 2016년 구축 시스템 — API 성숙도가 OCEAN-H보다 낮을 가능성. **위임 지원 여부**가 Phase 5 성립의 전제 |

### 5-3. RTDB (실시간 시계열)

| 항목 | 설계 |
|---|---|
| 주 Pattern | **P-ANALYZE**, **P-MONITOR** |
| 연계 방식 | **집계 API + 배치 복제** / 감시는 **이벤트 구독** |
| 필요 도구(예상) | 태그_검색(설비 기준) / 현재값_조회 / 구간통계_조회(평균·최대·최소) / 추이_조회(다운샘플링) |
| 선행 과제 | **★ 태그 ↔ 설비 ↔ 물리량 매핑** — 없으면 연계 자체가 불성립 |
| 특이사항 | 원시 데이터를 Agent 컨텍스트에 넣지 않음. **반드시 집계·요약 후 반환** |
| 검증 포인트 | **Phase 2-3에서 태그 1개월 구간 조회를 실제 수행** — 여기서 결론이 갈림 |

**RTDB 도구 설계 원칙 — 원시값 금지**
```
나쁨: 태그_이력_조회(태그, 시작, 종료) → 260만 포인트 반환 → Agent 컨텍스트 초과
좋음: 구간통계_조회(설비, 물리량, 시작, 종료, 집계단위)
      → {평균, 최대, 최소, 표준편차, 임계초과횟수, 대표추이 100포인트}
```

## 6. 전사 Endpoint/Gateway 반영 요건 (4-6 상세)

산출물을 **2갈래로 분리**합니다. 이것이 기획서 4페이지 "전사 공통/협의사안 vs. CLX 특화 과제"의 실체입니다.

### 6-1. (a) CLX 적용 기준 — 전사 방침 내에서 CLX가 지킬 것

| 영역 | 적용 기준 (예시 양식) |
|---|---|
| 인증 | 모든 Agent 호출은 전사 인증 체계를 경유. MCP Server도 예외 없음 |
| 인가 | 사용자 컨텍스트 전파 필수. Agent 고유 권한 단독 사용은 지정된 패턴에 한함 |
| 호출 제한 | Agent별 레이트리밋 설정. P-ANALYZE는 배치 경로로 우회 |
| 감사 | 호출 주체(사용자+Agent), 도구ID, 파라미터, 결과 건수를 로그에 기록 |
| 데이터 반출 | 대외비 등급 데이터는 외부 LLM API 컨텍스트에 포함 금지 |
| 명명·등록 | 전사 API 카탈로그 등록 규칙 준수 |

### 6-2. (b) 전사 협의·개선 요청 사항

Agent 연계는 기존 시스템 간 연계에 없던 요구를 만듭니다. 전사 표준이 이를 담고 있지 않을 가능성이 높습니다.

| # | 요청 사항 | 왜 필요한가 | 유형 |
|---|---|---|---|
| 1 | **Agent 신원 체계** 정의 | Agent가 권한 주체가 됨. SKT 사번 부여 방식 참조 | 표준 신설 |
| 2 | **권한 위임(OBO) 표준** | Agent가 사용자 대신 호출. 현행 표준에 없을 가능성 | 표준 신설 |
| 3 | **Agent 호출 감사 로그 규격** | 사용자+Agent 이중 주체 기록 | 표준 개정 |
| 4 | MCP Server의 Gateway 등록 방식 | 신규 유형의 클라이언트 | 표준 개정 |
| 5 | Agent용 레이트리밋 정책 | 사람과 호출 패턴이 다름 | 정책 신설 |
| 6 | **LLM 컨텍스트 반출 통제 기준** | 데이터가 모델 컨텍스트로 나감 | 보안 정책 신설 |
| 7 | 도구 카탈로그와 전사 API 카탈로그 관계 | 이중 관리 방지 | 거버넌스 정리 |

> 이 표가 **최종보고의 핵심 슬라이드 중 하나**가 됩니다. "CLX가 알아서 할 것"과 "전사가 정해줘야 할 것"을 분리해 제시하는 것이 경영층에 가장 잘 전달되는 형태입니다.

## 7. 비기능 설계 — 흔히 빠뜨리는 것들

### 7-1. 컨텍스트 예산 (Context Budget)
Agent는 무한한 데이터를 받을 수 없습니다. 도구 설계 시 **반환 크기 상한을 설계 제약으로** 다뤄야 합니다.

| 항목 | 기준(안) |
|---|---|
| 단일 도구 반환 | 기본 50행 / 최대 200행, 초과 시 페이징 |
| 텍스트 필드 | 1건당 2,000자 초과 시 요약 또는 잘라내기 + 원문 링크 |
| 시계열 | 원시값 금지. 집계값 + 대표 추이 100포인트 이하 |
| 총 컨텍스트 | Agent별 상한 설정, 초과 시 도구 호출 계획 재수립 |

### 7-2. 오류·폴백 설계
Agent는 오류를 받으면 **그럴듯하게 지어내는** 경향이 있습니다. 오류 응답 설계가 정확성 요건입니다.

| 상황 | 응답 설계 |
|---|---|
| 대상 미존재 | 빈 결과가 아니라 **"해당 설비ID 없음 + 유사 후보 3건"** |
| 권한 없음 | **"권한 없음"을 명시적으로 반환** (빈 결과로 처리하면 Agent가 "없다"고 답함 — 위험) |
| 부분 실패 | 성공 부분 + **실패 범위 명시** |
| 타임아웃 | 재시도 가능 여부와 대안 경로 안내 |
| 데이터 미정제 구간 | **"이 구간 데이터는 정제 미완료"** 플래그 반환 (OCEAN-H 20% 대응) |

> **"권한 없음"과 "데이터 없음"을 구분하지 않는 것**이 실무에서 가장 위험한 설계 결함입니다. Agent가 "그런 이력은 없습니다"라고 답하는데 실제로는 볼 권한이 없었을 뿐인 상황이 발생합니다.

### 7-3. 성능·부하
| 항목 | 기준(안) |
|---|---|
| P-READ 응답 | 2초 이내 |
| P-SEARCH 응답 | 5초 이내 |
| P-ANALYZE | 30초 이내 (초과 시 비동기 + 결과 조회) |
| 원천 부하 상한 | 운영 시스템 CPU 영향 5% 이내 → 초과 예상 시 복제 경로 |
| 캐싱 | 마스터성 데이터(설비 사양 등)는 캐시. 이력·실적은 캐시 금지 |
