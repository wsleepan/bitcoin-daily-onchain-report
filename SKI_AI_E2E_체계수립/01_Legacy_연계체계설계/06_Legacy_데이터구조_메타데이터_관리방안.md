# Legacy 데이터 구조 및 메타데이터 관리 방안

> 기대산출물: **Agent가 활용하기 용이한 Legacy 데이터 구조 및 메타 요건 정의**, **Agent-ready Data 설계 가이드 및 개선과제**
> 참조 아키텍처의 **L1(원천) · L2(의미) 계층**을 다룹니다. Phase 3의 심화 문서.

---

## 0. 이 문서의 명제

> **API는 Agent를 연결하지만, 메타데이터는 Agent를 정확하게 만듭니다.**

전통적 시스템 연계에서 메타데이터는 "있으면 좋은 것"이었습니다. 호출하는 쪽이 사람이 만든 프로그램이었고, 개발자가 사양서를 읽고 의미를 코드에 박아 넣었기 때문입니다.

Agent는 다릅니다. **런타임에 데이터의 의미를 스스로 해석**합니다. `STS_CD = '03'`을 받으면 그것이 무슨 뜻인지 추론하고, 근거가 없으면 **그럴듯하게 지어냅니다.** 그래서 메타데이터는 Agent 시대에 **정확성 요건**으로 승격됩니다.

이것이 이 과업이 "API 개발 프로젝트"가 아닌 이유입니다.

## 1. Agent-ready Data 5대 요건

| # | 요건 | 정의 | 미충족 시 증상 |
|---|---|---|---|
| **D1** | **식별 가능성** | 현장 언어로 표현된 대상을 시스템 식별자로 특정할 수 있음 | "3호기 압축기"를 못 찾음 |
| **D2** | **의미 명확성** | 컬럼·코드값의 업무 의미가 자연어로 기술됨 | 코드를 오해해 틀린 답 |
| **D3** | **시점 정합성** | 데이터의 시간 기준이 명확하고 시스템 간 변환 가능 | 다른 시스템 데이터와 시점이 안 맞음 |
| **D4** | **조회 단위 적정성** | Agent가 필요로 하는 단위로 잘라서 가져올 수 있음 | 전부 아니면 전무 |
| **D5** | **신뢰 표시** | 데이터의 정제 여부·품질·최신성이 함께 반환됨 | 미정제 구간을 사실로 답함 |

### D1. 식별 가능성 — 60만 기 설비의 문제

울산CLX 설비 60만 기 규모에서 이것은 **가장 먼저 풀어야 할 문제**입니다.

| 계층 | 현장 표현 | 시스템 표현 | 필요 조치 |
|---|---|---|---|
| 호칭 | "3호기 압축기", "No.3 컴프" | — | **별칭 사전** |
| 위치 | "2공장 3호기" | 플랜트–유닛 코드 | 위치 계층 매핑 |
| 설비 | — | `EQ-U3-C-0012` | 설비 마스터 (OCEAN-H) |
| 태그 | "토출 온도" | `TI-1203.PV` | **태그↔설비↔물리량 매핑** |

**설계 요건**
- 설비 마스터에 **별칭(Alias) 필드** 신설 — 현장 호칭, 약어, 구 명칭, 영문명
- **모호성 해소 규칙** — 후보 다수 시 반환 방식 (후보 목록 + 구분 정보 제공, 임의 선택 금지)
- 계층 롤업 — "3호기"로 물으면 하위 설비 전체를 대상으로 확장하는 규칙
- 별칭 수집 방법: ① 정비이력 자유서술에서 빈출 명사구 추출 ② 현업 인터뷰 ③ 기존 문서

### D2. 의미 명확성 — 시스템별 형태가 다름

| 시스템 | 의미 불명 형태 | 해결 산출물 |
|---|---|---|
| **OASIS** | 업무 상태 코드 (`STS_CD`, 품질판정, 승인단계) | **코드 사전** |
| **OCEAN-H** | 자유서술 이력(현상·조치), 정비유형 코드 | 코드 사전 + ②와 협업 |
| **RTDB** | 태그명 (`FIC-1203.PV`) | **태그 사전** |

### D3. 시점 정합성 — 시간축 표준

이것이 시스템 간 조인의 숨은 지뢰입니다.

| 시스템 | 시간 기준 | 문제 |
|---|---|---|
| RTDB | 절대 시각 (초/ms) | 기준 시간대(KST/UTC) 확인 필요 |
| OASIS | **생산일 · 교대** | 물리적 날짜와 다름 (예: 06:00~익일 06:00) |
| OCEAN-H | 작업일자, 발생일시 | 입력 시점 vs 발생 시점 구분 필요 |

**설계 요건**
- 표준 시간축 = **절대 시각(KST)** 으로 고정
- **생산일 ↔ 절대시각 변환 규칙** 문서화 (교대 경계, 일자 전환 시각)
- 도구 반환 시 **양쪽 표기 병행** — `{생산일: 2026-09-01, 교대: 야간, 절대구간: 2026-09-01T22:00 ~ 09-02T06:00}`
- "발생 시점"과 "입력 시점"이 다른 데이터는 **둘 다 반환**

### D4. 조회 단위 적정성
| 시스템 | Agent가 원하는 단위 | 현행 예상 | 조치 |
|---|---|---|---|
| OCEAN-H | 설비 1기 / 정비 1건 | 적정 | — |
| OASIS | 오더·배치·교대 | 적정 | 단위 간 변환 규칙 |
| **RTDB** | **집계값** (구간 평균·최대·편차) | 원시 포인트 | **집계 API 신설** |

### D5. 신뢰 표시 — 울산CLX 특화 요건

OCEAN-H 데이터 정제율이 **80% 이상**이라는 것은, 뒤집으면 **최대 20%가 미정제**라는 뜻입니다.
Agent는 미정제 구간에서 **오류를 내지 않고 틀린 답을 냅니다.**

**설계 요건**
- 데이터 정제 상태를 **레코드 또는 영역 단위 플래그**로 관리
- 도구 응답에 신뢰 메타 동반: `{정제상태: 검증완료 | 미검증, 최종갱신일, 출처}`
- Agent 프롬프트 규칙: 미검증 데이터 인용 시 **반드시 단서 표기**
- Phase 2에서 **미정제 20%가 어느 영역인지 식별** (설비유형별/공장별/연도별)

> 이 요건은 울산CLX의 실제 상황에서 도출된 것으로, 일반적인 Agent-ready 체크리스트에는 없습니다. **가장 실용적인 차별화 포인트**입니다.

## 2. 메타데이터 3계층 모델

메타데이터를 하나로 뭉뚱그리면 "누가 관리하느냐"에서 막힙니다. 3계층으로 나누면 소관이 갈립니다.

| 계층 | 내용 | 작성 주체 | 갱신 계기 |
|---|---|---|---|
| **M1. 기술 메타** | 테이블·컬럼·타입·키·제약, API 스펙 | 시스템 담당(IT) | 스키마 변경 시 |
| **M2. 업무 메타** ★ | 업무 의미, 코드값 뜻, 사용 주의사항, 별칭 | **현업 + 컨설턴트** | 업무 변경 시 |
| **M3. 운영 메타** | 정제 상태, 최종 갱신, 품질 지표, 사용 이력 | 시스템 자동 | 실시간·배치 |

> **M2가 이 과업의 핵심 산출물이고, 가장 만들기 어렵습니다.** M1은 시스템에서 추출되고 M3는 자동 생성되지만, M2는 **사람의 업무 지식을 글로 옮기는 일**입니다. 여기에 컨설팅 공수를 집중하십시오.

### M2 업무 메타 작성 표준

```
대상:        OASIS.ORDER_MST.STS_CD
업무 명칭:    작업오더 상태
업무 정의:    생산 작업오더의 진행 단계를 나타낸다.
코드값:
  01  계획      - 오더가 생성되었으나 아직 확정되지 않음. 변경 가능
  02  확정      - 생산 계획에 반영됨. 이 시점부터 자재 할당
  03  진행중    - 실제 생산이 시작됨
  04  완료      - 생산 종료. 실적 입력 완료
  09  취소      - 취소됨. 실적 없음
사용 주의:    - '완료(04)'는 실적 입력 완료를 뜻하며, 물리적 생산 종료와
                시차가 있을 수 있다 (최대 1교대).
              - 생산 실적 집계 시 09(취소)를 반드시 제외할 것.
              - 2023년 이전 데이터에는 02(확정) 단계가 없다.
관련 컬럼:    STS_CHG_DT (상태 변경 일시)
작성/검증:    생산관리팀 OOO / 2026-09-XX
```

**작성 규칙**
| 규칙 | 이유 |
|---|---|
| **코드값을 전부 나열** | 일부만 쓰면 Agent가 나머지를 추론 |
| **사용 주의사항 필수** | 집계 시 제외 조건 등은 Agent가 알 수 없음 |
| **과거 데이터의 예외 명시** | 체계 변경 이력이 조용한 오답의 원인 |
| **자연어 문장으로 기술** | Agent가 읽을 것을 전제. 표 형식 축약 지양 |
| **현업이 검증** | IT가 추정해 쓰면 틀림 |

## 3. 시스템별 메타데이터 설계

### 3-1. OASIS — 코드 사전

| 산출물 | 내용 | 규모 예상 |
|---|---|---|
| 업무 코드 사전 | 상태·유형·판정 코드 전체 | 수십~수백 코드셋 |
| 생산일·교대 정의서 | 시간축 변환 규칙 | 1건 |
| 집계 규칙서 | 실적 집계 시 포함·제외 조건 | 지표별 |

**우선순위 판정** — 전체 코드를 다루지 말고, **Phase 1 요구사항에 등장하는 코드부터** 착수합니다.

### 3-2. OCEAN-H — 설비 마스터 확장

| 산출물 | 내용 |
|---|---|
| **설비 별칭 사전** | 현장 호칭·약어·구명칭 ↔ 설비ID |
| 설비 계층 정의서 | 플랜트–유닛–설비–부품, 롤업 규칙 |
| 정비 코드 사전 | 정비유형·현상·조치 코드 |
| **정제 상태 맵** | 미정제 20% 영역 식별 결과 |
| 협력사 데이터 구분 | OCEAN-P 경유 데이터의 마스킹 대상 |

**활용 가능한 기존 자산** — OCEAN-H 구축 시 15종 시스템 통합·1,000만 건 전환 과정에서 **매핑·정제 산출물이 이미 존재**할 가능성이 높습니다. Phase 0에서 반드시 확보하십시오. 이것 하나로 Phase 3 공수가 크게 줄 수 있습니다.

### 3-3. RTDB — 태그 사전 ★ 최우선

**태그 사전이 없으면 RTDB 연계는 성립하지 않습니다.**

```
태그ID:      TI-1203.PV
물리량:      온도
단위:        ℃
대상 설비:   EQ-U3-C-0012 (3호기 압축기)
측정 위치:   토출부
정상 범위:   60 ~ 95
임계값:      High 105 / HighHigh 115
샘플링:      1초
보존:        원시 1년 / 1분 집계 5년
자연어 명칭:  "3호기 압축기 토출 온도"
동의 표현:   압축기 토출온도, 컴프 아웃렛 템프
비고:        2024-03 센서 교체. 이전 데이터와 절대값 편차 있음
```

**구축 방법** (태그가 수만~수십만 개일 것을 전제)
1. **태그 명명 규칙 역공학** — 기존 태그명 패턴 분석으로 자동 파싱 (`TI` = Temperature Indicator 등)
2. **DCS/제어 시스템 설정 정보 활용** — 태그–루프–설비 관계가 제어 설정에 이미 존재
3. **P&ID 도면 대조** — 설비와 계장의 물리적 연결
4. **현업 검증** — 자동 생성 결과를 설비·공정 담당이 확인
5. **우선순위 적용** — Phase 1 요구사항에 관련된 설비의 태그부터

> 전체 태그를 한 번에 하지 마십시오. **고장예측 과제 대상 설비의 태그**부터 시작하면, 이미 담당자가 파악하고 있는 범위라 검증이 빠릅니다.

## 4. 횡단 식별자 표준 (Phase 3-2 상세)

시스템 간 조인을 성립시키는 4개 축입니다.

| 축 | 기준 원천 (Master of Record) | 매핑 대상 | 산출물 |
|---|---|---|---|
| **설비** | **OCEAN-H 설비 마스터** | RTDB 태그, OASIS 오더의 설비 참조 | 설비↔태그 매핑표, 설비↔공정 매핑표 |
| **시간** | 절대 시각 (KST) | OASIS 생산일·교대, OCEAN-H 작업일자 | 시간축 변환 규칙서 |
| **공정·유닛** | (Phase 2에서 확정) | 3종 시스템 공정 코드 | 표준 공정 코드 + 매핑표 |
| **오더·배치** | OASIS | 설비·시간 구간 | 오더↔설비↔시간 매핑 규칙 |

### 구축 절차
1. Phase 2 진단에서 각 시스템의 현행 코드 체계 수집
2. 축별 기준 원천 지정 및 사유 문서화
3. **매핑 필요 여부 판정** — *이미 통일돼 있으면 이 과업은 크게 축소됩니다. 먼저 확인하십시오.*
4. 매핑 구축 방식 결정 (자동 생성 / 반자동 / 수작업)
5. **대표 횡단 질의 5건으로 검증** — 이 식별자만으로 조인되는가

### 검증 시나리오 (예)
> *"3호기 압축기 지난달 트립, 원인이 뭐고 생산에 얼마나 영향 있었나?"*

| 단계 | 필요 매핑 | 확인 |
|---|---|---|
| "3호기 압축기" → 설비ID | 별칭 사전 | ☐ |
| 설비ID → 트립 이력 (OCEAN-H) | — | ☐ |
| 트립 시각 → RTDB 조회 구간 | 시간축 | ☐ |
| 설비ID → 관련 태그 | **설비↔태그 매핑** | ☐ |
| 트립 시각 → 생산일·교대 | **시간축 변환** | ☐ |
| 생산일·교대 → OASIS 실적 | — | ☐ |
| 설비ID → 영향 공정 → 오더 | **설비↔공정 매핑** | ☐ |

> **이 표를 그대로 Phase 3의 검증 도구로 쓰십시오.** 체크가 하나라도 비면 그 매핑이 개선과제가 됩니다.

## 5. 메타데이터 저장·운영

### 5-1. 어디에 둘 것인가

| 방식 | 장점 | 단점 | 적합 |
|---|---|---|---|
| 각 시스템 내부 | 원천과 함께 관리 | 횡단 조회 불가, 표준 상이 | M1 일부 |
| **별도 데이터 카탈로그** | 횡단 관리, 검색 | 구축·동기화 비용 | **M2 중심 권장** |
| 도구 명세에 내장 | Agent가 바로 읽음 | 중복, 갱신 누락 | M2 요약본 |

**권장 구조** — 카탈로그를 **단일 원천(Single Source of Truth)** 으로 두고, 도구 설명은 **카탈로그에서 생성**합니다. 도구 설명을 수작업으로 따로 쓰면 반드시 어긋납니다.

```
[데이터 카탈로그 (M1+M2+M3)]
        │ 생성
        ├──→ 도구 설명 (L4 MCP/API 스펙)
        ├──→ Agent 프롬프트 컨텍스트
        └──→ 데이터 사전 문서 (사람용)
```

### 5-2. 거버넌스 R&R

| 역할 | 담당 | 책임 |
|---|---|---|
| 메타 총괄 | DT/데이터 조직 | 표준 정의, 카탈로그 운영 |
| 시스템 메타 담당 | 각 시스템 운영 조직 | M1 기술 메타 최신성 |
| **업무 메타 담당** | **현업 조직별 지정** | **M2 업무 의미 정의·검증** |
| 품질 모니터 | DT/데이터 조직 | M3 지표 측정, 미달 통보 |

> **현업 업무 메타 담당 지정이 이 방안의 성패를 가릅니다.** IT 조직 단독으로는 M2를 만들 수 없습니다. Phase 0에서 지정 가능 여부를 확인하고, 불가하면 **Phase 1 인터뷰에서 메타를 함께 수집**하는 방식으로 설계를 바꾸십시오.

### 5-3. 변경 관리 (Phase 6 연계)
